# AI 阅读助手上下文不足补充动作设计文档

## 背景

AI 阅读助手已经可以基于阅读统计、阅读画像、阅读记忆、复盘摘要、最近对话等上下文回答问题。近期截图中的回答在“数据不足时不强行给出高置信结论”这一点是正确的，但暴露出一个同类体验问题：

- 系统能说出缺少什么，例如划线内容、想法文本、书名主题。
- 用户不知道如何补充这些内容。
- 用户不知道当前数据状态是未授权、未同步、暂无数据、读取失败，还是数量不足。
- 用户不知道补充完成后是否会自动继续原问题。

这会让用户停在“我知道缺资料，但不知道下一步做什么”的状态。

## 目标

本次设计目标是：当 AI 因上下文不足无法给出高置信答案时，把“缺什么”转化为用户能立即执行的补充动作。

核心目标：

- 缺失项必须有明确补充入口。
- 缺失项必须展示当前状态。
- 补充动作必须说明补充后的用途。
- 补充完成后自动回到原任务继续生成。
- 保留低置信草稿能力，但必须明确标注准确度较低。
- UI 文案使用用户语言，不暴露“资源”“本地上下文”“信号”等内部概念。

## 非目标

本次不做：

- 不新增独立知识库或向量检索系统。
- 不改变 AI 阅读助手的主面板结构。
- 不强制接入新的远端服务。
- 不重做微信读书授权设置页。
- 不一次性支持所有可能的数据补充类型。
- 不在上下文不足时强制用户补全所有资料。

## 当前问题分析

### 1. 缺少补充路径

当前回答可能会说：

```text
缺少划线内容、想法文本、书名主题。
```

但用户并不知道下一步是：

- 同步微信读书划线。
- 选择本地已有划线。
- 粘贴几条划线文本。
- 先选择一本书。
- 生成或选择已有 AI 复盘。

因此“缺少 X”必须配套“如何补 X”。

### 2. 数据状态不清晰

同样是“缺少划线”，背后可能对应完全不同的状态：

- 未授权：还没有配置微信读书凭证。
- 未同步：有权限，但本地没有最新数据。
- 暂无数据：已同步，但用户确实没有划线。
- 读取失败：本地或远端读取失败。
- 数据不足：有少量数据，但不足以支撑高置信结论。

这些状态对应的行动入口不同，不能统一用“请提供划线资源”处理。

### 3. 系统概念过多

“本地上下文”“资源”“信号”“AI 资产”更接近系统内部概念。用户更容易理解：

- 已参考的内容。
- 还缺的内容。
- 可以补充的内容。
- 补充后会继续做什么。

### 4. 补充后闭环缺失

如果用户点击补充动作后还需要重新输入原问题，任务连续性会断开。系统应保留原始问题和当前线程，在补充完成后自动继续生成。

## 设计原则

### 1. 缺什么就给什么入口

每个缺失项都必须满足：

```text
缺失项 = 状态 + 补充入口 + 补充后用途
```

示例：

```text
最近划线：未同步
[同步最近划线]
同步后将用于提炼 3 个高频议题。
```

### 2. 优先推荐最小补充路径

多个资料同时缺失时，不要求用户一次性补齐。系统应推荐最小可行补充路径。

例如用户问“提炼 3 个高频议题”时，优先级是：

1. 最近 5 条划线或想法。
2. 当前书籍或最近阅读书籍。
3. 已生成的 AI 复盘或书籍复盘。
4. 阅读统计和阅读画像作为辅助依据。

### 3. 允许低置信继续

当已有弱信号但不足以得出可靠结论时，可以提供：

```text
先基于现有信息生成草稿
```

但必须标注：

```text
准确度较低，可补充划线或想法后优化。
```

### 4. 不让用户重新提问

补充数据完成后，系统应自动继续原始问题。原始问题应作为 pending task 保存在当前助手线程里。

### 5. 来源可查看

`阅读统计 · 1`、`最近对话 · 3` 这类来源标签应支持查看依据，或者改成更明确的用户语言：

```text
已参考：阅读统计 1 项、阅读画像 1 项、最近对话 3 条
```

## 推荐方案

### 方案 A：在回答下方追加“补充资料”动作区

这是 P0 推荐方案。

结构：

```text
我还缺少最近划线和想法内容，因此暂时不能可靠提炼 3 个高频议题。

目前只能看到两个倾向：
1. 最近阅读以有声内容为主。
2. 阅读节奏偏碎片化、轻量输入。

已参考：阅读统计 1 项、阅读画像 1 项、最近对话 3 条

补充后继续生成：
[同步最近划线] [粘贴想法] [先生成低置信草稿]
```

优点：

- 改动小，复用现有消息、建议按钮和 action 渲染模式。
- 不打断聊天流。
- 用户能在当前回答处直接完成下一步。

约束：

- 按钮文案必须短。
- 最多展示 3 个主动作。
- 低置信草稿必须排在补充动作之后。

### 方案 B：在上下文 chip 区展示数据状态

结构：

```text
已参考：阅读统计 1、阅读画像 1、最近对话 3
待补充：最近划线、想法
```

优点：

- 状态前置，用户在提问前就能看到上下文质量。

缺点：

- 容易让顶部 chip 区变重。
- 对首次使用用户可能过早暴露复杂状态。

### P0 选择

P0 采用方案 A，同时保留方案 B 的轻量来源文案优化。

理由：

- 当前问题发生在 AI 回答之后，动作应该跟随回答出现。
- 现有 `ReadingAssistantMessageOutput.suggestions` 已能承载追问按钮。
- 现有 `ReadingAssistantActionOutput` 已能承载结构化动作卡片，后续扩展成本低。

## 详细设计

### 1. 缺失上下文类型

P0 支持以下缺失项：

| 缺失项 | 用户文案 | 典型用途 |
| --- | --- | --- |
| `recentHighlights` | 最近划线 | 提炼主题、议题、复盘问题 |
| `recentThoughts` | 最近想法 | 识别关注点、困惑、行动意图 |
| `bookIdentity` | 书籍信息 | 限定回答范围，避免泛化 |
| `bookReviewSummary` | 书籍复盘 | 提供已整理的高密度上下文 |
| `readingStats` | 阅读统计 | 辅助判断周期、分类和节奏 |
| `readingPersona` | 阅读画像 | 辅助判断偏好和风格 |

P0 不直接暴露这些枚举名，只在代码层使用。

### 2. 缺失状态枚举

建议新增统一状态模型：

```ts
type ReadingAssistantContextGapStatus =
  | "missingPermission"
  | "notSynced"
  | "empty"
  | "readFailed"
  | "insufficient"
  | "available";
```

用户文案映射：

| 状态 | 用户文案 | 推荐动作 |
| --- | --- | --- |
| `missingPermission` | 未授权 | 去设置授权 |
| `notSynced` | 未同步 | 同步最近数据 |
| `empty` | 暂无数据 | 粘贴文本 / 选择其他书 |
| `readFailed` | 读取失败 | 重试读取 |
| `insufficient` | 数量不足 | 补充几条 |
| `available` | 已参考 N 条 | 查看依据 |

### 3. 回答输出扩展

建议在 `ReadingAssistantMessageOutput` 上扩展可选字段，保持向后兼容：

```ts
type ReadingAssistantContextGap = {
  contextType: string;
  label: string;
  status: ReadingAssistantContextGapStatus;
  itemCount?: number;
  message: string;
  actions: ReadingAssistantContextRecoveryAction[];
};

type ReadingAssistantContextRecoveryAction = {
  type:
    | "syncHighlights"
    | "pasteHighlights"
    | "syncThoughts"
    | "pasteThoughts"
    | "selectBook"
    | "generateBookReview"
    | "useLowConfidenceDraft";
  label: string;
  helperText?: string;
  payload?: Record<string, unknown>;
};
```

`ReadingAssistantMessageOutput` 增加：

```ts
contextGaps?: ReadingAssistantContextGap[];
confidence?: "high" | "medium" | "low";
continuationPrompt?: string;
```

约束：

- `contextGaps` 只描述缺失和恢复路径，不混入最终回答正文。
- `confidence` 只用于 UI 标识，不替代回答内容。
- `continuationPrompt` 用于补充完成后自动继续原任务。

### 4. UI 呈现

回答正文仍然承担判断和说明：

```text
我还缺少最近划线和想法内容，因此暂时不能可靠提炼 3 个高频议题。
```

结构化动作区承担恢复任务：

```text
补充后继续生成

最近划线：未同步
[同步最近划线]
同步后将用于提炼 3 个高频议题。

最近想法：数量不足
[粘贴想法]
补充后将用于归纳你最近关注的问题。

[先基于现有信息生成草稿]
准确度较低，可稍后补充资料优化。
```

视觉规则：

- 动作区使用轻量边框，不使用大卡片嵌套。
- 每个缺失项最多展示 2 个动作。
- 整个动作区最多展示 3 个主动作。
- 按钮文案控制在 10 个汉字以内。
- 状态文案不超过一行。

### 5. 推荐按钮文案

划线相关：

- `同步最近划线`
- `选择已有划线`
- `粘贴划线`

想法相关：

- `同步最近想法`
- `选择最近想法`
- `粘贴想法`

书籍相关：

- `选择最近阅读`
- `输入书名`

复盘相关：

- `生成书籍复盘`
- `选择已有复盘`

低置信继续：

- `先生成草稿`

不推荐：

- `帮我根据最近 5 条划线，提炼 3 个高频议题`
- `请根据我最近的想法记录，归纳我反复复盘在关注的问题`
- `为我列出适合生成 AI 复盘前需要补充的 5 类关键信息`

原因：按钮过长，且像问题而不是动作。

### 6. 补充后继续机制

当用户点击补充动作时，系统应记录：

- 当前线程 ID。
- 原始用户问题。
- 当前 AI 回答 ID。
- 缺失项类型。
- 补充动作类型。
- 补充完成后的 continuation prompt。

流程：

```text
用户提问
  -> AI 判断上下文不足
  -> 返回回答 + contextGaps + continuationPrompt
  -> 用户点击补充动作
  -> 完成同步 / 选择 / 粘贴
  -> 自动用原问题继续生成
  -> 新回答标记已参考新增资料
```

补充失败时：

```text
最近划线同步失败。你可以重试，或直接粘贴几条划线。
```

## 典型场景

### 场景 1：提炼高频议题但没有划线

用户：

```text
请结合我最近的划线和想法，提炼 3 个高频议题
```

系统：

```text
我还缺少最近划线和想法内容，因此暂时不能可靠提炼 3 个高频议题。

目前只能看到两个倾向：
1. 最近阅读以有声内容为主。
2. 阅读节奏偏碎片化、轻量输入。

已参考：阅读统计 1 项、阅读画像 1 项、最近对话 3 条
```

动作区：

```text
补充后继续生成
[同步最近划线] [粘贴想法] [先生成草稿]
```

### 场景 2：用户未授权微信读书

动作区：

```text
最近划线：未授权
[去设置授权] [粘贴划线]
授权后可同步最近划线，用于继续回答当前问题。
```

### 场景 3：已有少量资料

动作区：

```text
最近划线：已参考 2 条，数量偏少
[再同步一次] [先生成草稿]
```

### 场景 4：复盘缺失

动作区：

```text
书籍复盘：暂无
[生成书籍复盘]
生成后将作为高密度上下文，继续回答当前问题。
```

## 数据来源优先级

针对“提炼高频议题”类问题，推荐上下文优先级：

| 优先级 | 数据 | 说明 |
| --- | --- | --- |
| P0 | 最近划线 | 最直接反映关注内容 |
| P0 | 最近想法 | 最直接反映用户自己的问题 |
| P1 | 当前书 / 最近阅读书籍 | 限定主题边界 |
| P1 | 书籍复盘 | 已整理的高密度上下文 |
| P1 | 最近对话 | 补充用户当前意图 |
| P2 | 阅读统计 | 辅助判断周期和节奏 |
| P2 | 阅读画像 | 辅助判断偏好，不作为唯一依据 |

### 后端

建议落点：

- [src-tauri/src/services/ai.rs](../src-tauri/src/services/ai.rs)

后端工作：

- 在上下文构建阶段识别缺失项和状态。
- 在 AI 输出归一化阶段保留 `contextGaps`。
- 对明确需要划线、想法、书籍范围的问题增加上下文充足度判断。
- 当模型只返回正文时，服务端可基于上下文 bundle 补充结构化 `contextGaps`。

### 最小实现路径

P0 可以不先改模型 schema，而是服务端基于规则生成 `contextGaps`：

- 用户问题包含 `划线`、`摘录`、`高频议题`、`提炼`，但 `rawBookNotes` 或 `bookNotesSummary` 不足时，返回 `recentHighlights` gap。
- 用户问题包含 `想法`、`困惑`、`关注的问题`，但想法数量不足时，返回 `recentThoughts` gap。
- 用户问题包含 `这本书`、`最近读的书`，但缺少 `currentBook` 时，返回 `bookIdentity` gap。

这样可以降低对 AI 结构化输出稳定性的依赖。

## 验收标准

P0 验收：

- 当回答指出缺少划线时，同屏必须出现 `同步最近划线` 或 `粘贴划线`。
- 当回答指出缺少想法时，同屏必须出现 `粘贴想法` 或 `同步最近想法`。
- 当数据状态不同，文案能区分未授权、未同步、暂无数据、读取失败、数量不足。
- 用户点击补充动作完成后，不需要重新输入原问题。
- 已参考来源使用用户可理解的文案展示。
- 低置信草稿入口必须标注准确度较低。

P1 验收：

- 来源标签可查看依据。
- 支持选择已有划线、已有想法、已有复盘。
- 补充动作失败后提供替代路径。

P2 验收：

- 支持按问题类型自动推荐最小补充路径。
- 支持上下文质量评分。
- 支持用户在设置中调整“低置信草稿”的默认策略。

## 风险与约束

### 1. 动作过多导致噪音

约束：

- 同屏最多 3 个主动作。
- 同一缺失项最多 2 个动作。
- 默认推荐最小补充路径。

### 2. 状态判断不准

约束：

- P0 只判断已有明确本地数据的状态。
- 无法确认时使用 `insufficient`，不要伪装成 `empty`。

### 3. 低置信草稿被误认为正式结论

约束：

- 低置信回答必须在正文和来源区都标注。
- 不把低置信结果写入长期阅读记忆，除非用户确认。

### 4. 补充流程打断聊天

约束：

- 补充动作必须保留当前线程。
- 补充完成后自动继续生成。
- 补充失败时回到原消息动作区。

## 任务拆分

### P0

- 定义 `ReadingAssistantContextGap` 和 `ReadingAssistantContextRecoveryAction`。
- 在后端上下文构建阶段输出基础缺失项。
- 前端渲染补充动作区。
- 优化来源标签文案。
- 支持 `先生成草稿`。

### P1

- 支持同步、粘贴、选择三类补充入口。
- 补充完成后自动继续原问题。
- 来源依据可查看。

### P2

- 上下文质量评分。
- 最小补充路径推荐。
- 低置信草稿策略设置。
