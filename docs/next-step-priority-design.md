## 1. 文档目的

本文不重新定义产品方向，也不增加新的用户能力，而是把当前工作区的实际实现状态与现行 M1/M2 规划对齐，确定下一开发周期的主执行顺序、阶段门禁和验收口径。允许在不破坏依赖、不扩大用户承诺的前提下并行处理独立切片。

当前产品已经具备书架、笔记、统计、书籍复盘、阅读指南、选书决策、本地阅读器、Markdown/Obsidian/Notion 导出等主要能力。T0-T7 已经依次修复权限漂移、迁移恢复、三维状态写入、决策缓存语义、真实笔记三态和基础队列规则分散；下一阶段的主要风险收敛为以下三类一致性问题：

1. SQLite 旧列与读取兼容仍须保留到正式版本验证完成；T7 已将候选/待整理资格、排序、去重和兼容回退收敛到 selectors，上一正式版应用的旧列读取仍留在 T9 复验。
2. Windows/Android/Web 回归和上一正式版兼容仍须在 T9 / M1 RC 收口；仓库级 Rust 格式已在进入 T9 前恢复为通过状态，T9 仍需在最终全量门禁中复验。
3. 总览、统计、成果等页面仍有重复入口，但其收敛依赖 M1 的 selectors 和 glossary，不应越级实施。

因此，本周期采用“先恢复可信基线，再完成 M1，最后启动 M2”的顺序。

## 2. 设计原则

### 2.1 先修正确性，再改结构

测试、权限、类型和数据语义未恢复可信基线前，不进入依赖这些基础的跨页面结构重构。Obsidian、Notion 或 AI 方向只处理安全、数据丢失、兼容性和构建阻断问题，不新增模板、入口或产品承诺。

### 2.2 写操作只修改自己的维度

候选身份、阅读生命周期、整理进度必须保持正交。任何按钮只能 patch 自己负责的字段，不得用整行覆盖顺带改变其他状态。

### 2.3 未知就是未知

没有加载真实笔记数据时使用 `undefined` 或显式的 `unknown/loading` 状态，不使用 `1`、`0` 或缓存外推值制造“可生成”的假象。

### 2.4 一条规则只有一个实现

候选队列、待整理队列和后续 TodayPlan 必须由纯 selector 统一计算。页面只负责渲染和导航，不各自维护排序、排除和去重逻辑。

### 2.5 每个阶段独立可回滚

质量门禁、前端状态接线、诚实性修复、词典治理和 M2 启动拆成独立切片。任何切片失败都可以单独回退，不要求一次完成全部重构。

## 5. P0：质量门禁恢复设计

### 5.1 命令注册单一清单

当前命令同时出现在三个层次：

1. `src-tauri/src/lib.rs`：运行时 `generate_handler!` 注册；
2. `src-tauri/build.rs`：构建期生成 command permission；
3. `src-tauri/capabilities/default.json`：主窗口允许调用的 permission。

新增本地命令时三处必须同步。P0 先补齐：

```text
validate_notion_credential
patch_reading_item_state
```

对应 capability ID：

```text
allow-validate-notion-credential
allow-patch-reading-item-state
```

更新 `build.rs` 后重新运行 Tauri/Cargo 构建流程，并确认 `src-tauri/permissions/autogenerated/` 出现对应 TOML 文件。生成文件由 Tauri 构建配置产生，不手工维护文件内容；若生成结果未进入版本控制，则测试和 CI 必须先执行生成步骤，不能依赖开发机残留产物。

### 5.2 防回归机制

保留 `src/lib/tauri-permissions.test.ts` 作为门禁，并扩展为双向集合检查。准确关系应为：

```text
registered local commands
= build.rs local command manifest
= autogenerated local command permissions
= default capability 中的 allow-* 本地命令权限
```

`core:*`、`opener:*`、`dialog:*`、移动插件等非本地命令权限不参与上述等式。至少应检测：

- `lib.rs` 有命令但 `build.rs` 没有；

## 6. P1：M1 状态模型前端接线设计

### 6.1 目标模型

前端统一使用三个正交维度：

```ts
type ReadingItem = {
  itemId: string;
  itemKind: "book" | "album" | "mp" | "localBook";
  isCandidate: boolean;
  candidateSource?: "weread" | "ai_unconfirmed" | "ai_confirmed" | "light";
  lifeStatus: "none" | "want" | "reading" | "paused" | "finished" | "dropped";
  finishedSource?: "weread_auto" | "manual";
  organizeStatus: "none" | "to_organize" | "organized";
  userNote?: string;
  sourceMeta?: ReadingItemSourceMeta;
};
```

三个维度的职责：

| 维度 | 回答的问题 | 典型字段 |
| --- | --- | --- |
| 来源身份 | 它是什么、从哪来、是否候选 | `itemKind`、`isCandidate`、`candidateSource` |
| 生命周期 | 用户现在想不想读、读到哪种状态 | `lifeStatus`、`finishedSource` |
| 整理进度 | 是否需要整理、是否完成整理 | `organizeStatus` |

### 6.2 API 设计

新增：

```ts
patchReadingItemState(itemId, patch, meta?)
```

行为要求：

- 记录存在时只更新 patch 中出现的字段；
- 记录不存在时必须提供 meta 才能创建；
- 清空 `userNote` 使用显式 `clearUserNote`；
- 前端对未知枚举采用保守回退，并通过不包含凭据、原始响应或本地绝对路径的诊断记录暴露兼容问题；
- `sourceMeta` 在 Rust/前端边界上必须明确采用“JSON 字符串传输、前端解析为对象”或统一对象协议，不能同一字段两种形态并存；
- Web 预览 normalizer 与 Tauri 返回结构保持一致。

旧 `upsertReadingItemState()` 在迁移期只作为兼容层存在，不再接受新增调用。所有调用迁移完成后删除前端 API 与运行时命令注册；数据库旧列和 Rust 读取兼容字段至少保留一个正式发布版本，后续是否清理按第 15.1 节兼容窗口另行设计。

### 6.3 接口示例与错误契约

创建不存在的候选记录：

```ts
await patchReadingItemState(
  "book-123",
  {
    isCandidate: true,
    candidateSource: "ai_unconfirmed",
    sourceMeta: {
      savedFrom: "assistant",
      aiReason: "补充当前主题的实践视角"
    }
  },
  {
    itemKind: "book",
    title: "示例书",
    author: "示例作者"
  }
);
```

更新已存在记录的整理状态：

```ts
await patchReadingItemState("book-123", {
  organizeStatus: "organized"
});
```

从已读完恢复为在读时，调用方只表达目标生命周期，服务端负责清理不再适用的 `finishedSource`：

```ts
await patchReadingItemState("book-123", {
  lifeStatus: "reading"
});
```

前端 API 负责把对象形态的 `sourceMeta` 序列化为 Rust 当前接收的 JSON 字符串，并把响应字符串解析回对象。页面和组件不得直接 `JSON.stringify/parse`，避免协议逻辑散落。

命令错误沿用 `{ code, message, detail? }`：

| 错误场景 | 建议 code | 页面处理 |
| --- | --- | --- |
| itemId 为空、枚举非法、空 patch、字段冲突 | 现阶段沿用 `invalid_gateway_payload`；后续可评估更名为 `invalid_payload` | 原位提示，不重试 |
| 记录不存在且无 meta | `invalid_gateway_payload` | 刷新当前状态；仍不存在则补 meta 重试 |
| sourceMeta 非法 JSON/结构不合法 | `invalid_gateway_payload` | 保留用户操作上下文，提示更新失败 |
| SQLite 读写或迁移失败 | `local_storage_error` | 显示通用恢复提示，允许导出脱敏诊断 |
| capability 拒绝或命令未注册 | 运行时框架错误，前端归一为本地能力不可用 | 引导升级/重启，不循环重试 |

`detail` 只用于诊断，不直接作为主提示。不得包含 API Key、Authorization、数据库绝对路径、用户原始笔记/AI 理由全文或未脱敏的 SQL 参数。`sourceMeta` 结构校验除合法 JSON 外，还应拒绝非对象顶层、未知超长键值和超过整体长度上限的输入。

### 6.4 写入点迁移

| 页面/动作 | 只允许修改 |
| --- | --- |
| 发现页保存候选 | `isCandidate`、`candidateSource`、`sourceMeta.savedFrom` |
| 书籍详情加入候选 | 同上，不碰生命周期和整理进度 |
| 标记待整理/已整理 | `organizeStatus` |
| 复盘页标记已整理 | `organizeStatus` |
| 书架保存有声书/文章候选 | 候选维度，`candidateSource: "light"` |
| AI 推荐加入候选 | 候选维度及 `sourceMeta.aiReason` |
| 候选确认真实书源 | `candidateSource`、`sourceMeta.confirmedAt` |
| 开始读/暂缓/读完 | 生命周期维度 |
| 删除记录 | 仅通过显式二级操作调用 remove，不与“暂缓”混用 |

### 6.6 字段不变量与归一化

仅校验单字段枚举不够，服务层还必须保证字段组合有明确语义：

| 不变量 | 规则 |
| --- | --- |
| `itemKind` | 创建后不可通过 patch 修改；现有记录传入的 meta 仅用于缺失记录创建，不更新书目元数据 |
| `isCandidate` / `candidateSource` | `isCandidate=true` 时必须能从当前记录或本次 patch 得到合法来源；改为 false 时保留来源和 `sourceMeta` 作为历史出处，供暂缓负样本使用 |
| `lifeStatus` / `finishedSource` | 进入 `finished` 时未提供来源则归一为 `manual`；离开 `finished` 时必须清空 `finishedSource`；非 finished 状态不得携带新 finishedSource |
| `userNote` | `userNote` 与 `clearUserNote=true` 不得同时出现，避免“清空优先还是设值优先”的歧义 |
| `sourceMeta` | 采用整体替换语义；调用方更新 `confirmedAt` 时必须保留已有 `savedFrom`、`aiReason` 等键 |
| 空 patch | 拒绝不含任何有效字段的 patch，避免只刷新 `updatedAt` 干扰候选队列排序 |
| `updatedAt` | 只有发生有效状态修改时刷新；读取和无操作请求不得改变 |

当前 Rust 实现对 `finishedSource` 的清空和空 patch 拒绝尚无完整表达。实现时优先在服务层根据 `lifeStatus` 推导 SQL `CASE`，不额外把数据库细节暴露给页面；若最终采用 `clearFinishedSource`，必须同步 Rust/TypeScript 类型、API 映射和测试。

### 6.7 状态转换矩阵

| 用户动作 | 原状态要求 | 原子 patch | 保留内容 | 结果 |
| --- | --- | --- | --- | --- |
| 加入候选 | 任意未删除记录 | `isCandidate=true` + 合法 `candidateSource` | 生命周期、整理状态、备注 | 成为候选，不覆盖其他维度 |
| 开始读 | 候选或想读 | `lifeStatus="reading"` | 候选身份、来源、整理状态 | 进入在读；若原为 finished，清空 finishedSource |
| 标记读完 | 任意非 dropped | `lifeStatus="finished"` + `finishedSource="manual"` | 候选身份、整理状态 | 手动读完，自动同步不得覆盖来源 |
| 微信自动读完 | 进度与完成时间满足条件 | 后端置 `finished` + `weread_auto` | 候选身份、整理状态 | 不覆盖 manual 或 dropped |
| 暂缓候选 | 当前为候选 | `isCandidate=false` + `lifeStatus="dropped"` | 来源、备注、整理状态 | 保留负样本与历史出处 |
| 恢复候选 | 有历史来源 | `isCandidate=true` + 目标 `lifeStatus` | 来源和备注 | 恢复为候选；页面必须让用户明确选择想读/在读 |
| 标记待整理 | 有可处理内容 | `organizeStatus="to_organize"` | 候选、生命周期、备注 | 进入统一待整理队列 |
| 标记已整理 | 已生成或已确认成果 | `organizeStatus="organized"` | 候选、生命周期、备注 | 从待整理建议中排除 |
| 清除整理状态 | 任意记录 | `organizeStatus="none"` | 其他全部维度 | 不等同删除记录 |
| 删除记录 | 用户二级确认 | `removeReadingItemState` | 无 | 物理删除本地状态记录 |

“暂缓”当前沿用蓝图的 `dropped` 存储值。UI 是否同时展示“暂缓”和“放弃”两个不同文案，需要在详情页控件实施时核对；若产品确实需要两个不同语义，必须先扩展领域枚举，不能让两个按钮写入同一值却声称含义不同。

### 6.8 Patch 并发与合并语义

M1 不引入版本号或乐观锁。普通字段采用“按字段 patch、最后一次有效写入生效”，不同维度并发写入不会互相覆盖。例外是 `sourceMeta` 整体替换：

- 页面提交前应基于当前记录合并键值；
- 候选确认写入 `confirmedAt` 时必须保留 AI 理由和保存入口；
- 同一条记录的多个异步动作应串行等待，按钮在请求中禁用；
- 返回值必须以服务端最终记录刷新页面状态，不在本地猜测合并结果。

M1 不增加数据库级 revision；若实际回归出现同字段并发丢失，再单独评估 `expectedUpdatedAt`，不预先扩大协议。

### 6.9 不变量测试

必须建立以下回归测试：

- 加入候选不会清除 `organizeStatus`；
- 标记已整理不会清除候选身份；
- 标记在读不会移除候选；
- 离开 finished 会清空 `finishedSource`，进入 finished 默认来源为 manual；
- AI 候选确认不会覆盖 `userNote` 或已有 `sourceMeta` 键；
- `userNote` 与 `clearUserNote` 冲突时拒绝请求；
- 空 patch 被拒绝且不刷新 `updatedAt`；
- “暂缓”保留记录，“删除记录”才移除；
- 自动同步读完不覆盖手动 `dropped` 或 `finished_source: manual`；
- 同一迁移执行两次结果一致。

## 11. 非功能质量要求

### 11.1 性能与响应性

- `listReadingItemStates` 按当前产品规模设计，目标在 5,000 条状态记录下本地查询与映射 P95 小于 200ms；超出时先补索引和分页评估，不在页面静默截断数据。
- 单条 patch 的数据库事务 P95 目标小于 100ms，不包含 UI 动画和进程通信开销。
- 三维回填在 10,000 行样本下目标小于 5 秒；超过 500ms 时启动界面应展示“正在升级本地数据”，不得呈现无响应白屏。
- 迁移和大列表映射不得在 React 渲染循环中执行重复 JSON 解析；`sourceMeta` 在 API 边界解析一次。
- 性能数字为工程目标，不是当前实测结论；T1/T2 需要建立可重复基准并记录机器与数据规模。

### 11.2 事务与一致性

- add-column、备份、回填当前并非全部处于同一事务；实现前必须明确失败点和可重入行为。回填事务失败后，新增空列可以保留，但下次启动必须可靠重试，且不能把“列已存在”误判为迁移完成。
- 备份完成到回填开始之间若应用退出，下一次启动必须复用已有备份并继续回填，不重复灌入。
- 所有 patch 采用单条 SQL 原子更新并返回同一连接读到的最终记录。
- selectors 只消费一次一致的状态快照，不在计算途中分别拉取多个版本的数据。

### 11.3 可用性与可访问性

- 状态控件不能只用颜色表达候选、在读、读完、待整理和已整理；必须有文本或可访问名称。
- 所有按钮保持可键盘聚焦、可回车/空格触发，操作中提供 `disabled`/`aria-busy`，错误提示与触发控件建立可感知关联。
- “删除记录”需要二级确认；“暂缓”“标记在读”“标记已整理”等可逆动作不额外制造阻塞式确认。
- 紧凑模式、浅色/深色主题和 Android 触摸目标不能因三组状态控件退化。

### 11.4 隐私与安全

- 状态数据、用户备注、AI 理由和阅读上下文默认只保存在本地；本轮不新增上传。
- 输入长度在 Rust 服务层再次校验，不能只依赖前端。
- `sourceMeta` 只允许已知键；未知键采用拒绝或显式丢弃并记录类别，不能原样长期沉淀任意内容。
- 诊断导出由用户手动触发，并复用既有敏感信息过滤；新增事件遵守第 13.5 节最小字段原则。

### 11.5 跨端一致性

- Windows、Android 和 Web 共享 TypeScript 领域映射与 selectors；平台差异只留在能力调用和导航层。
- Tauri 命令参数、返回字段和错误结构在 Windows/Android 一致；Web mock 必须模拟同一返回契约。
- 桌面和 Android 正式产物使用同一应用版本与数据 schema 语义，避免移动端先写入桌面端不认识的状态。

## 12. 风险与控制

### 12.1 新旧状态并存

**风险**：迁移期间一部分页面写新字段，另一部分页面仍整行覆盖旧字段。
**控制**：API 接线完成后按页面连续迁移；在迁移完成前禁止新增旧 upsert 调用；用静态搜索和测试作为合并门禁。

### 12.2 capability 与构建清单漂移

**风险**：运行时已注册命令，但构建清单和权限文件遗漏，直到测试或打包时才暴露。
**控制**：扩展权限一致性测试，未来新增命令必须同时更新三处清单。

### 12.3 文案替换引发 E2E 大面积失败

**风险**：测试依赖中文文本定位。
**控制**：先迁移为稳定 testid，再引入 glossary 和禁用词检查。

### 12.4 导出能力继续扩张干扰收口

**风险**：Obsidian/Notion 已有较大改动面，继续增加模板、同步或追踪功能会与设置、成果和导出中心重构冲突。
**控制**：M1/M2 期间只修阻断测试、数据丢失或安全边界的问题，其余新能力进入 M4 导出中心统一设计。

### 12.5 大型 E2E 文件不可维护

**风险**：页面结构重构导致单个 smoke spec 冲突和定位困难。
**控制**：在 M2 PR-10 前后按 Dashboard、Stats、Outcomes、Settings 等页面拆分 spec，同时保留一条端到端主闭环 smoke。

### 12.6 M2 共享缓存遗漏

**风险**：统计与解读合并后，Dashboard、ReadingHub、Notes 仍独立拉取书籍复盘概览，生成新复盘后不同页面显示不一致。
**控制**：M2 将 `listBookNotesSummaries` 收敛为 App 级缓存，并在复盘生成/更新后发送失效事件；该项是 M2 数据一致性任务，不提前塞进 M1。

### 13.6 迁移对账报告

迁移函数除成功/失败外，应在内部生成结构化对账摘要，至少包含：

```ts
type ReadingStateMigrationSummary = {
  totalRowsBefore: number;
  pendingRows: number;
  scanned: number;
  updated: number;
  unchanged: number;
  backupRows: number;
  byLegacyType: Record<string, number>;
  byLifeStatus: Record<string, number>;
  byOrganizeStatus: Record<string, number>;
  invalidRows: number;
};
```

该摘要默认只进入脱敏本地日志；设置页仅在迁移异常时展示简化结果。这里明确采用“只备份待迁移行”的方案，与当前 `db.rs` 的 `WHERE life_status IS NULL` 行为一致。选择理由是迁移表只服务于本次字段回填回滚，体积可控且避免与应用级全库备份职责重叠。以下断言失败时迁移整体失败并回滚回填事务；若失败发生在回填事务开始前，则中止启动并保留已创建的新列和备份，供下一次幂等重试：

- `pendingRows = scanned`；
- `scanned = updated + unchanged`；
- 迁移后主表总行数等于 `totalRowsBefore`；
- 首次迁移时 `backupRows = pendingRows`；已有备份时不得追加或覆盖，且必须验证其覆盖本次待迁移 itemId 集合；
- `invalidRows = 0`，否则保留原行并中止发布升级；
- 二次执行 `pendingRows = 0`、`updated = 0`，`backupRows` 不变化。

如果实施评审决定把 `reading_item_states_backup_v1` 改为全表快照，必须同步修改表命名/职责、备份 SQL、恢复流程、体积测试和上述断言；不能只改 `backupRows` 的期望值。

### 13.7 T1 实施结果（2026-08-01）

- `open_connection()` 在 `initialize_schema()` 前检测旧 schema 或 `life_status IS NULL` 行，只有确需迁移时创建固定目录 `backups/reading-state-v1-pre-migration`。
- 自动备份先执行 WAL checkpoint，再复制 SQLite 主文件并写兼容既有恢复流程的 `manifest.json`；随后验证备份文件可打开且包含 `reading_item_states`。
- 已有有效备份只校验和复用，不覆盖；目录已存在但数据库或 manifest 不完整时安全失败，防止半成品被静默覆盖。
- 待迁移行备份表只在首次不存在时写入；已有空备份、行数不符或缺少任一 pending itemId 时拒绝回填。
- 未知历史 `item_type`、非法状态组合或非法 `sourceMeta` 计入 `invalidRows`，在任何行更新前中止。
- 回填事务在 COMMIT 前校验主表总数不变、`scanned = updated + unchanged` 且剩余 pending 为 0；失败会回滚本次回填。
- 自动化已覆盖首次备份、有效备份复用、当前 schema 跳过、不完整目录拒绝、旧库恢复后再次升级、迁移映射、未知类型拒绝、陈旧备份拒绝、二次幂等和应用级备份/恢复往返。
- T1 文件已单独通过 rustfmt 与 `git diff --check`。仓库级 `cargo fmt --check` 仍只报告同工作区其他 Rust 切片（`commands/settings.rs`、`export/notion.rs`、`services/reading_state.rs`）的格式差异，不包含本轮 `db.rs`/`services/settings.rs`。

## 14. 验收场景脚本

以下场景作为测试设计和手工验收的共同语言。自动化测试可以拆分执行，但不得改变 Given/When/Then 的业务结论。

### 14.1 候选与整理状态正交

**Given** 一本书已经 `isCandidate=true` 且 `organizeStatus=to_organize`。
**When** 用户在详情页重新确认候选来源。
**Then** `candidateSource/sourceMeta` 更新，`organizeStatus` 仍为 `to_organize`，生命周期和 userNote 不变。

### 14.2 标记已整理不移除候选

**Given** 一本候选书已经生成书籍复盘。
**When** 用户点击“标记已整理”。
**Then** 仅 `organizeStatus=organized`，候选身份、来源和生命周期保持不变；该书从待整理队列排除，但仍可在候选书架看到。

### 14.3 暂缓与删除可区分

**Given** 一本 AI 推荐候选带有 `aiReason`。
**When** 用户选择“暂缓”。
**Then** 记录保留，`isCandidate=false`、`lifeStatus=dropped`，来源和理由仍可供后续决策排除。
**When** 用户选择二级确认后的“删除记录”。
**Then** 本地状态记录被移除。

### 14.4 完成来源归一

**Given** 一本书由微信同步自动标记 `finished + weread_auto`。
**When** 用户重新标记为在读。
**Then** `lifeStatus=reading` 且 `finishedSource` 清空。
**When** 用户随后手动标记读完。
**Then** `finishedSource=manual`，后续自动同步不得覆盖。

### 14.5 真实笔记生成门禁

**Given** 页面只有书目元数据，真实笔记数量未知。
**When** 用户进入书籍复盘页。
**Then** 页面进入 loading，生成按钮不可用。
**When** 请求返回 `exportableCount=0`。
**Then** 页面引导同步或写想法，不允许生成。
**When** 返回大于 0。
**Then** 显示真实来源统计并允许手动生成。

### 14.6 决策缓存严格匹配与失败降级

**Given** 已有候选集 A、因子 X、窗口 90 天生成的缓存。
**When** 候选、因子或窗口任一变化后查询最新决策。
**Then** 返回空缓存，不展示旧结果。
**When** 用户触发生成且 AI 请求失败。
**Then** 可以显示最近缓存，但必须同时展示失败原因、生成时间和“非当前输入结果”的降级说明。

### 14.7 旧数据升级与二次启动

**Given** 数据库包含 candidate/toRead、reviewing、organized、AI 魔法 note 和轻候选。
**When** 首次启动新版本。
**Then** 创建可恢复备份，所有旧行按矩阵回填，主表行数不减少。
**When** 再次启动。
**Then** `pendingRows=0`、迁移更新行数为 0，状态和 `backupRows` 不变化。

### 14.8 capability 完整性

**Given** `lib.rs` 注册一个本地命令。
**When** 执行权限契约测试。
**Then** build manifest、autogenerated permission 和 default capability 必须存在对应项。任一缺失时测试失败并列出命令名。

### 14.9 Web 保守降级

**Given** Web 预览 fixture 含未知的未来枚举。
**When** 页面映射并渲染该记录。
**Then** 使用 `none/undefined` 等保守值，不把记录显示为“读完”“已整理”或“已确认候选”，同时产生脱敏诊断。

### 14.10 M2 完整闭环预留

**Given** 用户在选书决策结果页选择一本推荐书。
**When** 用户在两次点击内标记在读或打开微信读书。
**Then** 该书保留候选身份并进入 `lifeStatus=reading`；次日 TodayPlan 可将其作为继续读主动作。该场景在 M1 只验证 patch 能力，在 M2 PR-13/PR-8 中完成端到端验收。

## 15. 部署、升级与兼容策略

### 15.1 Schema 兼容窗口

- 新版本写新维度，同时保留旧 `item_type/status/note` 至少一个正式发布版本。
- 兼容窗口内，旧版本应能忽略新列并继续读取旧列；新版本读取未回填行时必须通过 COALESCE/派生规则保守兼容。
- 在决定删除旧列前，必须确认最低支持版本、活跃版本分布和 Android/Windows 同版本覆盖；删除列属于新的迁移设计，不附带在普通重构 PR 中。
- M1 不将新状态反向同步回旧三列作为长期双写方案；兼容依赖旧列保留和旧版可运行，不建立两套事实源。若回退后旧 UI 看不到新状态变化，发布说明必须明确这一限制。

### 15.2 构建产物一致性

本地 RC 阶段允许使用明确标记的 Windows 无签名 NSIS 与 Android debug APK 做隔离安装、升级和兼容验收，但这两类产物不得作为正式发布签名证据，也不得上传或更新远端清单。

同一正式发布版本必须同时核对：

- Windows 安装包及更新清单/签名；
- Android 签名 APK；
- Web 预览构建和预览数据版本；
- Tauri autogenerated permissions；
- README、用户指南和发布说明中的版本与术语。

禁止前端版本相同但 Rust 命令 manifest、capability 或 schema 语义不同的产物进入同一 Release。

### 15.3 分批发布

推荐顺序：

1. 本地 RC：脱敏备份副本迁移、全量自动化。
2. Windows/Android 内部验证：升级、重启、回退、重新升级。
3. GitHub 预发布：小范围下载，重点收集迁移和 permission 错误。
4. 稳定发布：确认无停止推广条件后更新 latest manifest。

项目当前未定义强制远程遥测，因此“观察”以用户主动诊断、GitHub 反馈和可复现实验为主，不虚构实时失败率。若未来引入遥测，需单独隐私设计和用户选择。

### 15.4 升级说明必备内容

- 状态模型从单枚举升级为候选/生命周期/整理三个维度；
- 首次启动可能进行本地数据升级，升级前会创建备份；
- 选书决策 prompt v2 会造成旧缓存正常不再命中，但历史资产仍可查看；
- 产品术语新旧对照；
- Windows 与 Android 应升级到同一版本；
- 回退旧版本时，新维度变更可能无法在旧 UI 中完整显示。

## 16. 回滚策略

- capability 修复可单独回退，不改变用户数据。
- 前端 patch 接线按页面独立提交；某页面出现问题时可回退该页面，但不得删除数据库新字段或备份表。
- 数据迁移保留旧列和 `reading_item_states_backup_v1` 至少一个正式发布版本；是否在 M2 后清理必须另开迁移设计并确认活跃版本兼容窗口，不能在本设计中自动授权删列。
- glossary 只约束新源码和现行文档，必要时可临时扩大明确白名单，但不可关闭检查。
- M2 页面合并必须保留旧路径重定向，确认发布版本稳定后再清理死代码。

## 18. 暂停与升级条件

出现以下任一情况时，暂停当前切片，不继续扩大修改面：

1. 迁移前备份无法创建、校验或恢复。
2. 新旧版本对同一数据库产生不可逆兼容问题。
3. patch 迁移后出现候选、生命周期或整理状态丢失。
4. Android 与 Windows 对同一命令返回结构不一致。
5. Web 预览无法保守映射新增枚举，出现误导性状态。
6. AI 决策输入变化后仍命中旧 hash，或失败降级无法明确标识。
7. glossary 检查需要大面积豁免才能通过，说明词典边界或扫描范围设计不合理。

暂停后必须记录：触发条件、影响数据、可逆性、临时处置和恢复门槛。涉及数据丢失或迁移不可逆时，回到设计评审，不以兼容分支继续掩盖。

## 21. 评审与变更控制

### 21.1 Definition of Ready

任务进入实现前必须满足：

- 上位问题编号、所属 PR 和 T0-T9 任务已确认；
- 依赖任务已完成或明确可并行；
- 涉及的状态字段、写入动作和不变量已列出；
- 需要的 fixture、备份副本或跨端设备可用；
- 已明确自动化测试与手工验收证据；
- 数据迁移、权限或缓存语义变化已写入 PR 风险说明；
- 没有把 M2/M3/M4 的能力偷偷并入 M1。

不满足 Ready 时允许做只读探索、测试夹具准备和短 ADR，不开始业务实现。

### 21.2 Definition of Done

任务完成必须同时满足：

- 代码、测试、文档和 capability/build manifest 同步更新；
- 相关 Given/When/Then 场景有可追溯证据；
- 无新增旧 upsert、魔法 note、伪笔记数或淘汰术语；
- 错误信息和诊断日志符合脱敏边界；
- 任务对应的追踪矩阵已更新；
- 回滚方式经过验证或有明确的兼容路径；
- 发现的未解决问题已创建后续任务，不藏在注释或临时分支中。

### 21.3 评审角色与关注点

| 角色 | 必审内容 |
| --- | --- |
| 数据/后端评审 | 迁移事务、备份恢复、字段不变量、兼容旧列、错误脱敏 |
| 前端评审 | API 编解码、状态刷新、并发按钮、空态/错误态、Web 预览 |
| 产品评审 | 暂缓/放弃语义、词典、唯一入口、是否扩大用户承诺 |
| 测试评审 | 迁移样本、跨端矩阵、E2E 稳定定位、回滚演练 |
| 发布评审 | 版本一致、签名产物、升级说明、推广暂停条件 |

小切片可以一人承担多个角色，但检查项不能省略。涉及数据库迁移和删除旧命令的 PR 至少需要一次独立复核。

### 21.4 文档变更规则

- 本文服从 `functional-consolidation-blueprint.md`；冲突时先更新上位裁决，再更新本文。
- 修改已确认决策时，必须在第 24.1 节表中记录新结论、理由和影响任务。
- 新增字段、枚举或错误码时，必须同步状态矩阵、接口示例、迁移样本、测试矩阵和 glossary。
- 修改任务依赖时，必须同步第 19、20 节以及相关提交切片。
- 删除验收项需要说明为何不再覆盖原问题编号，不允许因测试困难直接删除。
- 文档中的测试数量、版本和当前状态都是时点快照；实现 PR 应引用实际命令结果，不复制旧数字。

| 状态写入 | 维度级 patch | 避免候选、生命周期、整理状态互相覆盖 |
| patch 并发 | M1 不引入 revision；字段级最后有效写入，sourceMeta 调用前合并 | 控制范围，先解决现有覆盖问题 |
| `finishedSource` | 离开 finished 必须清空 | 防止 reading/paused 携带错误完成来源 |
| 暂缓语义 | 当前存储为 `dropped`；如要区分“暂缓/放弃”必须扩枚举 | 避免两个按钮同值不同义 |
| 未知笔记数 | 不使用占位数字 | 诚实性原则与生成门禁 |
| 决策缓存 | 正常路径严格 hash；失败路径允许明确降级 | 区分正确性与可用性 |
| 迁移备份范围 | `reading_item_states_backup_v1` 只备份首次执行时 `life_status IS NULL` 的待迁移行；首次迁移前另建固定目录全库备份 | 行级对账与全库灾备分责，且自动备份已接入 schema 初始化前 |
| 自动备份覆盖策略 | 已有有效备份只复用；任何不完整或非法备份安全失败，不自动覆盖 | 避免覆盖唯一可恢复的迁移前副本 |
| 旧数据库列 | 至少保留一个正式版本 | 回滚与活跃版本兼容 |
| 导出/Notion 扩展 | 本轮只修风险，不新增承诺 | 避免与 M4 导出中心重复设计 |
| M2 并行方式 | 两条主路线 + 独立 PR-13 | 遵循 M2 文件依赖和冲突边界 |

### 24.2 尚需实施阶段确认

- 自动备份复用的具体调用位置与用户可感知行为；
- `sourceMeta` 跨 Rust/TypeScript 的最终序列化协议，以及是否保留整体替换或在后端提供 merge；
- 旧列清理所需的活跃版本兼容窗口；
- Android 手工回归设备矩阵；
- E2E 拆分的文件边界与共享 fixture 组织方式。

这些事项可以在对应切片开始前通过短 ADR 或 PR 说明确认，不应阻塞 P0 权限门禁修复。

### 24.3 最终结论

最终评审判断：本设计已覆盖 M1 收口所需的产品语义、数据迁移、接口不变量、权限门禁、测试发布、跨端兼容、回滚、隐私、可访问性和任务追踪，没有发现需要在 T0 前新增的阻断性设计章节。当前剩余不确定项均已收敛到第 24.2 节，可在对应任务进入实现前用短 ADR 或 PR 说明裁决，不应继续扩展为新的 M1 用户能力。

| 评审维度 | 结论 | 进入实现前要求 |
| --- | --- | --- |
| 范围 | 合理，无需继续扩大 M1 | 坚持第 23 节非目标，不夹带 M2-M4 功能 |

| 发布准备 | 设计完整，实证未完成 | T9 提交第 9、13-15 节的实际证据，不沿用本文快照数字 |

下一步主推荐顺序为：

```text
恢复权限与测试门禁
→ 完成 M1 前端状态模型接线
→ 清除伪数据与错误缓存语义

```
