- 对已移出书架的结果，详情入口会先按 `bookId` 拉取书籍详情并刷新本地进度，再进入详情页；如果本地没有可刷新数据，仍显示待确认，不把笔记存在直接推断为已读完。

## 2. 截图证据与现状

用户在阅读助手中输入：

```text
我读过富爸爸的书吗
```

当前链路是：

```text
用户问题
  -> General
  -> 阅读统计 + 阅读画像 + 阅读记忆
  -> Provider 生成“无法确认”
```

同一用户在本地笔记书库输入“富爸爸”时，已经可以看到至少以下有笔记的书：

- 《富爸爸穷爸爸》
- 《富爸爸成功创业的10堂必修课》
- 《富爸爸投资指南》

这说明部分书名、作者、阅读进度和笔记数量已经存在于本地数据中，但不能据此断言完整书架只有这几本。完整书目仍必须以书架、书籍详情和阅读进度为主，笔记汇总只作为可选的数量补充。缺口不是向量召回失败，而是两个入口没有共享“按书名/标题前缀查本地书籍”的结构化查询能力。

## 3. 问题与根因

### 3.1 意图覆盖不足

现有 `CategoryBooksQuery` 要求同时出现书目列举词、阅读状态词和分类词，例如“我读过哪些理财类书籍”。“富爸爸”是书名或系列实体，不是分类别名，因此不会命中分类书目路由。

### 3.2 数据入口分裂

笔记书库和书架页可以在前端按书名或作者筛选，但 AI 阅读助手没有调用同一个后端结构化查询服务。Provider 只能看到聚合统计，无法凭空还原具体书名。

### 3.3 与远端微信读书搜索边界不清

“我读过富爸爸的书吗”是在问本地阅读事实；“微信读书有《富爸爸穷爸爸》吗”是在问远端可用性。两者不能共用一个会调用远端搜索的 action。

### 3.4 书名和系列名不等价

“富爸爸”可能是系列前缀，也可能只是用户输入的模糊关键词。系统应返回匹配候选并说明匹配方式，不能把模糊匹配直接宣称为官方系列归属。

## 4. 目标与非目标

### 4.1 目标

- 支持按本地书名、标题前缀、作者确认用户是否读过相关书籍；标题前缀只表示相关书籍匹配，不宣称官方系列全集。
- 返回每本匹配书籍的阅读状态、进度和笔记数量，并支持点击进入书籍详情。
- 使用书架、书籍详情和阅读进度建立统一后端查询；可复用规范化规则，但不直接依赖前端内存筛选，不调用 Provider 生成书名。
- 与分类书目查询、单书笔记检索、跨书笔记检索和微信读书远端搜索保持清晰路由边界。
- 当结果不完整或匹配有歧义时，显示可验证的缺口和下一步，而不是统一返回“无法确认”。

### 4.2 非目标

- 不使用向量相似度判断书籍是否被阅读。
- 不根据笔记主题推断书名、系列归属或阅读状态。
- 不把本地阅读记录查询改造成远端微信读书搜索。
- 不在首期引入复杂的自然语言 SQL 或通用实体知识图谱。
- 不承诺官方系列全集；只返回本地可确认的匹配记录。

## 5. 用户体验

### 5.1 本地书名/系列查询

用户输入：

```text
我读过富爸爸的书吗
```

助手返回结构化结果卡片：

```text
本地记录中找到 3 本与“富爸爸”匹配且有阅读证据的书

《富爸爸穷爸爸》 · 有阅读记录 · 进度 98% · 426 条笔记
《富爸爸成功创业的10堂必修课》 · 已读完 · 进度 99% · 235 条笔记
《富爸爸投资指南》 · 有阅读记录 · 进度 13% · 10 条笔记

依据：本机书籍详情、阅读进度和本地笔记记录。
```

示例中的 `98%` 只表示没有额外完成证据时的状态；如果同一本书同时存在明确完成标记、完成时间或手动本地完成状态，仍可显示“已读完”。因此，完成判断不能只看百分比，也不能把 `95%~98%` 无条件提升为完成。

结果卡片必须区分：

- `已读完`：有完成标记、完成时间、手动本地完成状态，或助手书目查询中的进度达到 99%。
- `有阅读记录`：存在进度、阅读时长或阅读记录，但没有完成证据。
- `未发现本地阅读记录`：本地有书籍元数据，但没有可验证的阅读证据。

### 5.2 指定完成状态

```text
列出我读完的富爸爸系列书
```

只返回完成证据成立的书籍；若本地有匹配书但尚未读完，在卡片中显示“有阅读记录”，不能混入已读完列表；只有书籍元数据、没有阅读证据的书不应进入“我读过”的主列表，但必须通过 `unconfirmedBooks` 作为“匹配但待确认”的补充信息展示。用户可以逐本打开详情刷新进度；系统不能把笔记存在直接推断为已读完。

### 5.3 结果为空或有歧义

- 没有本地匹配：说明“本机没有找到包含该关键词的书籍记录”，并提供“使用《书名》格式重新查询”的建议。
- 有书籍匹配但没有阅读证据：说明“找到书籍元数据，但没有确认的阅读记录”。
- 匹配过多：先展示前 N 条稳定排序结果，并提示“关键词匹配到 N 本，建议补充作者或完整书名”。
- 只有远端可用性结果：不得把“微信读书可找到”写成“你读过”。

## 6. 路由模型

### 6.1 查询类型

将书目查询统一抽象为：

```ts
type BookCatalogQueryKind = "category" | "title" | "author";

type BookCatalogQuery = {
  kind: BookCatalogQueryKind;
  targetText: string;
  readFilter: "hasEvidence" | "started" | "finished" | "allLocalBooks";
  itemKind: "book";
  limit: number;
};
```

现有分类查询保持 `kind = "category"`。本次新增 `title` 和 `author`。用户输入“富爸爸系列”时仍使用 `kind = "title"`，通过 `matchReason = "titlePrefix"` 表示标题前缀匹配，不引入没有数据基础的官方 `series` 类型。

### 6.2 意图优先级

```text
用户问题
  -> 明确的笔记内容查询       -> NoteSearchQuery / LibraryNoteSearchQuery
  -> 本地阅读事实 + 书名目标   -> BookCatalogQuery(title|author)
  -> 本地分类书目查询          -> BookCatalogQuery(category)
  -> 明确的微信读书可用性查询  -> WereadAvailabilitySearch
  -> 其他                     -> General
```

本地阅读事实优先于远端搜索：

- 出现“我读过、我看过、我读完、我的阅读记录、进度”等本地事实信号，并能抽取书名/作者目标时，优先走 `BookCatalogQuery`。
- 出现“笔记、划线、想法、摘录”并要求找内容时，优先走笔记检索；书名只作为笔记检索范围，不改走书目查询。
- 出现“微信读书有没有、搜索一下、能不能找到、加入候选”等远端可用性信号，且没有本地阅读事实语义时，才走 `WereadAvailabilitySearch`。
- “我没读过、还没读、只想收藏”等否定或候选语义不得被解释为 `hasEvidence`；无法确定目标和状态时返回澄清，而不是调用 Provider 猜测。

### 6.3 书名/标题前缀目标抽取

按以下顺序提取 `targetText`：

1. `《书名》`、中文引号或英文引号中的文本。
2. “某某系列”“某某的书”“某某相关的书”中的核心短语，但查询类型仍是 `title`。
3. 去除“我读过、有没有、哪些、书、系列、读完、读过”等查询词后的剩余实体短语。

无法得到稳定实体短语时，不调用 Provider 猜测，返回澄清提示：

```text
请提供书名、系列名或作者，例如《富爸爸穷爸爸》或“富爸爸系列”。
```

## 7. 本地数据查询

### 7.1 数据来源

查询服务聚合现有本地结构化数据：

- 书架记录：是否在书架、书籍基础元数据；
- 书籍详情：规范化书名、作者、分类；
- 阅读进度：进度百分比、完成标记、完成时间；
- 本地阅读状态：开始/完成/最近阅读证据；
- 笔记统计：`notebook_books` 中的划线数、想法数、总笔记数；
- 同步时间：各来源的 `updatedAt` 或最近一次同步时间。

不得将阅读统计聚合表作为书名明细唯一来源，也不得从向量文档反推书籍事实。

书架和书籍详情是完整书目候选来源；`notebook_books` 只补充笔记数量，不得因为一本书没有笔记而从完整书目中删除。查询“书”默认只匹配 `itemKind = "book"`，不混入有声书、文章收藏或其他书架条目。

结果必须带数据新鲜度：

- 所有必要来源均可查询：`complete`；
- 书目、进度或笔记统计只有部分来源：`partial`；
- 没有可用书籍元数据：`unavailable`。

P1.6 不引入任意“过期阈值”来否定已有本地结果；界面展示 `sourceUpdatedAt`，由用户决定是否需要同步。

### 7.2 匹配规则

匹配顺序建议为：

1. 规范化标题完全匹配；
2. 标题前缀匹配，用于系列词，例如“富爸爸”；
3. 标题分词匹配；
4. 作者匹配；
5. 规范化别名匹配（仅限已有本地别名，不由模型生成）。

每条结果记录 `matchReason`：`exactTitle`、`titlePrefix`、`titleToken`、`author` 或 `alias`。`titlePrefix` 只表示标题匹配方式，UI 不得把它显示成官方系列归属。

书名规范化只处理大小写、空白、常见标点和全半角差异；不能删除会改变书名语义的词，也不能把相似书名合并为同一本书。

### 7.3 去重与排序

- 以稳定 `bookId` 为主键去重。
- 同一 `bookId` 的多来源字段保留来源集合。
- 排序优先级：完全匹配、标题前缀匹配、阅读完成证据、阅读进度、最近阅读时间、稳定 `bookId`。
- 首期固定最多返回 20 条，超过上限设置 `truncated = true` 并提示用户补充完整书名或作者；不在 P1.6 引入新的交互式分页游标。

## 8. 输出契约

内部统一使用 `BookCatalogOutput`；历史 `categoryBooks` action 只作为旧消息读取兼容层，不再维护第二套查询和排序逻辑。

```ts
type ReadingAssistantBookCatalogOutput = {
  queryKind: "category" | "title" | "author";
  queryText: string;
  queryStatus: "found" | "partial" | "empty" | "ambiguous";
  matchedMetadataCount: number;
  matchedReadingCount: number;
  listedCount: number;
  truncated: boolean;
  message: string;
  unconfirmedBooks?: BookCatalogItem[];
  books: Array<{
    bookId: string;
    title: string;
    author?: string;
    category?: string;
    matchReason: "exactTitle" | "titlePrefix" | "titleToken" | "author" | "alias";
    readStatus: "finished" | "started" | "unknown";
    progressPercent?: number;
    totalNoteCount?: number;
    highlightCount?: number;
    thoughtCount?: number;
    sources: Array<"shelf" | "detail" | "progress" | "localState" | "notebookBooks">;
  }>;
  diagnostics: {
    catalogCoverage: "complete" | "partial" | "unavailable";
    missingReasons?: Array<
      | "bookMetadataNotSynced"
      | "readingStateMissing"
      | "noteSummaryMissing"
      | "progressNotSynced"
      | "queryAmbiguous"
    >;
    sourceUpdatedAt?: {
      catalog?: string;
      progress?: string;
      noteSummary?: string;
    };
  };
};
```

数量口径固定如下：

- `matchedMetadataCount`：按书名/作者命中的本地书目数量，尚未应用阅读证据过滤；
- `matchedReadingCount`：其中具有阅读证据的数量；
- `listedCount`：实际显示的条目数量，受 20 条上限影响；
- `unconfirmedBooks`：命中书目但被本次阅读状态过滤掉的条目，最多展示 20 条；不计入 `listedCount`，也不计入已确认主列表；
- `truncated`：是否因上限省略了其余匹配项。

`basisNotice` 示例：

```text
基于本机书籍详情和阅读进度确认；笔记数量来自本地笔记汇总，不代表微信读书远端书库结果。
```

简单本地书目确认不调用聊天 Provider；只有用户继续要求解释、比较或分析这些书如何影响阅读观时，才将已确认书目作为结构化上下文交给 Provider。

## 9. UI 改造

### 9.1 书目结果卡

复用现有分类书目卡的视觉样式，但标题从分类专用文案改为查询语义：

```text
本地记录中找到 3 本与“富爸爸”匹配且有阅读证据的书
```

每条结果显示：

- 书名、作者；
- 已读完/有阅读记录；`allLocalBooks` 查询时才额外显示无阅读证据；
- 进度；
- 划线、想法和总笔记数；没有同步到笔记汇总时显示“笔记统计未同步”，不显示为 0；
- 匹配方式（可放在辅助信息或详情中）；
- 点击进入书籍详情或笔记页。

不要显示“统计 34 本”作为书名列表数量，除非它与 `matchedMetadataCount` 的数据范围和过滤条件完全一致。

### 9.2 依据与状态

- `found`：显示实际匹配数量和书目列表；
- `partial`：显示已列出的数量和缺口原因；如果主列表为空但存在 `unconfirmedBooks`，显示待确认书单和详情入口；
- `empty`：显示无本地记录，不引导用户误以为远端也没有；
- `ambiguous`：显示匹配数量和补充关键词入口。

当用户查询“我读过”时，主列表只显示 `readStatus = "started" | "finished"` 的记录；只有元数据匹配但没有阅读证据的书显示在 `unconfirmedBooks` 补充列表中。若书已移出书架，仍可通过详情、进度或本地完成状态确认；缺少这些来源时必须保持 `unknown`。

当书目缓存缺失或不完整时，结果卡提供明确的 `同步书架` CTA；同步完成后由用户重新发起查询，避免把旧结果自动替换为新结果。单本阅读进度仍通过已有的书籍详情入口刷新，不新增一个无法覆盖全部书籍的伪“同步进度”动作。同步失败时应显示失败原因，不自动调用 Provider。

普通回答的 `basisNotice` 与 `bookCatalog` action 分开显示，避免“阅读统计 +1”遮蔽结构化书目结果。

### 9.3 旧消息兼容

- 历史 `categoryBooks` 消息继续按原卡片渲染；
- 新的通用书目结果使用同一张书目卡，通过 `queryKind` 切换分类、书名和作者标题；
- 未识别新字段时，前端降级显示书名和基本阅读状态，不使整条消息失败。

## 10. 隐私与 Provider 边界

| 场景 | 是否调用 Provider | 发送内容 |
| --- | --- | --- |
| 本地书名/标题前缀确认 | 否 | 无 |
| 本地分类书目查询 | 否 | 无 |
| 基于已确认书目做比较/分析 | 是 | 书名、作者、分类、阅读状态和覆盖边界 |
| 单书笔记主题检索 | 视索引和授权而定 | 查询文本；命中正文仅在原始笔记授权开启时发送 |
| 微信读书可用性搜索 | 是远端搜索接口 | 用户明确提交的搜索关键词 |

书名查询不会因为启用了语义索引而自动发送笔记正文，也不会因为关闭原始笔记授权而无法查询本地书目事实。

## 13. 风险与取舍

- 未维护官方系列字段时，“系列查询”只能表示标题前缀或关键词匹配，应在 UI 中使用“相关书籍”而非“系列全集”。
- 书名规范化过度可能造成误匹配，因此必须保留原始标题和匹配原因。
- 本地书籍元数据和阅读状态可能来自不同同步时点，`partial` 结果必须可见。
- 笔记中心和书架页目前是不同的前端内存筛选入口，不能假设已有可直接复用的后端搜索服务。
- 通用书目查询层会扩大现有 action 契约，需要保留旧 `categoryBooks` 解析以兼容历史消息，但内部不维护两套查询实现。
- 这项改造解决的是书目事实查询，不会自动解决跨书笔记主题召回或完整复盘的覆盖问题。
