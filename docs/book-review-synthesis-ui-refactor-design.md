## 2. 背景与问题

书籍复盘页现在同时提供两条不同的 AI 生成路径：

1. **普通复盘**：从当前笔记中取有限样本，一次调用聊天 Provider。
2. **快照式全量归纳**：固定当前笔记快照，按章节分批调用 Provider，再合并为正式书籍复盘。

两条路径的最终产物都叫“书籍复盘”，但当前 UI 没有清楚表达覆盖范围：

- 普通按钮只写“生成复盘”，没有显示本次会使用多少条笔记。
- 全量任务卡使用“快照式全量笔记归纳”这一实现术语，默认直接出现在页面主流程中。
- 创建快照与开始调用 Provider 是两个动作，当前授权文案容易让用户误解发送时机。
- 任务完成后，当前会话可以显示完成进度，但刷新页面后完成任务不再属于活动任务，卡片会重新显示授权入口。
- 全量结果虽然在后端以独立 prompt 版本优先保存和读取，但页面来源标签仍可能只显示“本地缓存”，用户无法判断当前内容是否覆盖了完整快照。

这会导致用户无法回答最基本的问题：**当前看到的复盘到底使用了多少笔记？**

## 3. 设计目标

1. 在生成前明确区分“快速复盘”和“完整复盘”。
2. 在生成后明确展示覆盖量、批次、快照时间和 Provider 模型。
3. 页面刷新后仍能恢复最近一次已完成全量任务的完成态。
4. 不改变现有全量任务的快照、分批、恢复、取消和失败重试语义。
5. 不让向量索引、普通笔记检索或阅读助手状态混入书籍复盘的来源说明。
6. 保持授权边界可见：只有用户确认并开始任务后，原始笔记正文才发送到对应 Provider。

## 4. 非目标

- 不将普通复盘改造成全量任务。
- 不让向量索引参与书籍复盘生成。
- 不改变 Provider、模型、Key 或快照存储策略。
- 不在本次改造中重写书籍复盘内容结构。
- 不把任务历史做成通用任务中心；本次只保留当前书最近一次相关任务。

## 5. 现有输入边界

### 5.1 普通复盘

以下是本次稳定抽样改造前的历史行为基线，不能与文档顶部“已实现”的目标行为混读：

- 最多 80 条划线；
- 最多 80 条想法；
- 每条笔记正文最多 700 字符；
- 章节、时间、星标等结构化元数据；
- 当前按数组顺序分别截取，存在前部笔记和早期章节被过度代表的偏差；
- 不包含全书正文，也不保证覆盖全部笔记。

本次改造的目标预算为：

- 最多 80 条划线；
- 最多 20 条想法；
- 总预算最多 100 条，但实际纳入数分别不能超过本地可用数。

因此，对于 488 条划线、20 条想法的书，普通复盘最多使用 100 条笔记。UI 必须把“本次纳入数”和“本地可用数”分开显示，不能只显示本地总数；文案应使用“最多”，不能暗示每次必然使用固定数量。预算调整属于行为变更，需同步更新 Prompt 输入统计、缓存输入哈希和测试夹具。目标行为落地后，当前实现说明、选择摘要和结果元数据都必须以 `stableChapterStratified` 为准，不再把数组顺序截取描述为现行规则。

### 5.2 快照式全量归纳

全量任务当前使用：

- 创建时的固定笔记快照；
- 单条快照正文最多 8,000 字符；
- 每批正文预算约 12,000 字符；
- 按章节和笔记类型稳定分批；
- 空正文和归一化后的重复正文不重复发送；
- 完成条件为快照项目和批次均已处理，且不存在失败批次。

因此“全量”表示**对快照项目完成可验证覆盖**，不是表示每条正文永远不受任务预算限制。UI 应展示已有的跳过/重复统计；截断数量只有在后端提供结构化字段时才展示具体数字。

### 5.3 普通复盘抽样规则（目标行为）

普通复盘不采用每次变化的纯随机抽样，也不继续使用固定顺序截取。推荐使用**稳定伪随机 + 按章节分层抽样**：在有限预算内尽量覆盖更多章节，同时保证同一份输入重复生成时拿到同一批笔记。

#### 5.3.1 采样输入和排序键

候选笔记先按类型拆分为划线和想法，并为每条候选构造稳定键：

```text
documentKey = sourceType + ":" + sourceId
chapterKey  = chapterUid || normalizedChapterTitle || "__unclassified__"
priority    = SHA-256(bookId + "|" + samplingVersion + "|" + sourceType + "|" + documentKey)
```

约束：

- `sourceId` 必须使用数据库中的稳定业务 ID，不能使用数组下标或 `randomUUID()`；
- `samplingVersion` 纳入输入哈希，算法升级后不会错误复用旧缓存；
- 不把当前时间、请求 ID 或调用次数放入种子；
- 未分章笔记统一进入“未分章”分层；
- 同一笔记的显示顺序只用于最终 Prompt 可读性，不参与是否入选。

#### 5.3.2 配额分配

对每一种笔记类型独立执行，避免划线再次把想法挤出预算：

```text
sample(candidates, budget, bookId, sourceType):
  if candidates.length <= budget:
    return all candidates sorted by canonical order

  strata = group candidates by chapterKey
  order strata by SHA-256(bookId + "|" + samplingVersion + "|" + sourceType + "|" + chapterKey)

  # 章节数超过预算时，只保留稳定排序最前面的 budget 个章节；
  # 否则每个非空章节先分配 1 个名额。
  coveredStrata = first min(strata.length, budget) strata
  quota[stratum] = 1 for coveredStrata
  remaining = budget - sum(quota)

  # 剩余名额只在 coveredStrata 内按候选数比例分配，使用最大余数法解决舍入；
  # 某个分层达到自身上限后，将未用名额继续分配给其他未满额分层。
  repeat distribute remaining proportionally by coveredStrata candidate count
    cap each quota at stratum candidate count
    redistribute any leftover until remaining == 0 or all strata are full
  within each stratum, select notes with the smallest stable priority
  return selected notes sorted by canonical order
```

其中 `canonical order` 固定为 `chapterUid`（无值时使用规范化章节标题）、章节标题、`sourceType`、`sourceId`、内容哈希，不能直接沿用调用方数组顺序。该顺序只负责 Prompt 的可读性和结果复现，不改变前面的入选决策。

实现时需要处理以下边界：

- 候选总数不超过预算时不做无意义抽样，全部纳入；
- 空正文是否计入候选数必须与当前普通复盘行为保持一致，并在 API 中明确；
- 配额因上限截断后仍有剩余名额时，按未满额分层继续分配，直到预算耗尽或没有候选；
- `chapterKey` 为空的笔记不能被丢弃，只能归入“未分章”；
- 最终实际纳入数以选中笔记数为准，不能直接写成预算上限。

这不是面向用户的“抽签”功能，也不在首版增加“换一批”按钮。若未来需要多视角重采样，应显式增加用户可追溯的 `samplingRunId`，不能让同一结果在刷新或重试时无故变化。

#### 5.3.3 采样元数据和缓存

普通复盘请求和结果中增加可选的选择摘要，不发送哈希种子的原始值：

```json
{
  "selection": {
    "strategy": "stableChapterStratified",
    "samplingVersion": "book-review-sampling-v1",
    "highlightBudget": 80,
    "thoughtBudget": 20,
    "availableHighlightCount": 488,
    "availableThoughtCount": 20,
    "includedHighlightCount": 80,
    "includedThoughtCount": 20,
    "coveredChapterCount": 27,
    "coverage": "sampled"
  }
}
```

输入哈希必须包含：书籍 ID、候选笔记稳定 ID、正文规范化后的内容哈希、章节键、`samplingVersion` 和两个预算值。相同输入重复生成应命中同一选择结果；新增、删除或算法版本升级时重新计算选择，正文修改会使缓存输入哈希失效并重新生成，但在候选集合和章节元数据不变时允许保持相同的文档 ID 集合。UI 可据此显示：

```text
最多使用 100 / 508 条
划线最多 80 / 488 · 想法最多 20 / 20
按章节分层抽样，覆盖 27 个章节；不代表全量覆盖
```

## 6. 页面信息架构

### 6.1 顶部生成区

保留单本复盘页的主操作区，但把两个动作改成明确的产品语言：

```text
快速复盘
最多使用 100 / 508 条
按章节分层抽样，不代表全量覆盖

完整复盘
覆盖当前快照中的 508 条，预计 111 批
```

推荐按钮文案：

- 普通路径：`生成快速复盘`
- 已有普通结果：`重新生成快速复盘`
- 全量路径入口：`创建完整复盘任务`

普通路径下方应补充一句：

```text
适合快速查看主题和行动建议；本次最多纳入 80 条划线和 20 条想法，按章节分层抽样，不会逐条处理整本书的全部笔记。
```

当实际可用数小于预算时，按实际数显示，例如：

```text
最多使用 35 / 40 条
划线最多 25 / 30 · 想法最多 10 / 10
按章节分层抽样，不代表全量覆盖
```

这里的“最多使用”是预算上限，不是承诺每次都会填满 100 条。无论本次是否命中缓存，选择摘要都应和结果一起保存，避免页面重新计算后与历史结果不一致。

### 6.2 全量任务卡

全量卡默认作为次级区域展示，标题使用用户语言：

```text
完整复盘
覆盖当前书的全部可处理笔记
```

卡片摘要显示：

- 本地笔记：`508 条`
- 划线/想法：`488 / 20`
- 预计批次：`111 批`
- 当前 Provider 和模型

未创建任务时，授权文案必须准确说明时机：

```text
我确认：开始完整复盘后，当前快照中的原始笔记正文会发送给 Provider（r-api / 模型名）。
```

按钮使用：

```text
创建本地快照
```

创建快照本身不发送正文。创建成功后，卡片必须明确显示第二个网络动作：

```text
开始发送并归纳
```

只有点击该按钮后，快照中的原始笔记正文才发送给 Provider。这样保留隐私授权的可见边界，不把本地快照创建和远程调用伪装成同一个动作。

### 6.3 任务进行中

进行中卡片显示：

```text
完整复盘进行中
已处理 320 / 508 条
批次 8 / 111
阶段：正在归纳批次
模型：模型名
```

操作：

- `取消任务`
- 失败时显示 `重试失败批次`
- 不展示不可靠的剩余时间承诺

### 6.4 完成态

完成态必须是可持久恢复的成果状态，而不只是当前会话的进度状态：

```text
完整复盘已完成
已覆盖快照：508 / 508 条
划线 488 · 想法 20 · 111 批
生成时间：2026-08-17 12:30
模型：模型名

[查看完整复盘] [复制完整复盘] [导出完整复盘]
```

完成态下不再显示授权复选框，也不显示“继续调用 Provider”。

若存在跳过项目，在完成信息下补充：

```text
跳过重复 3 条 · 空正文 1 条
```

只有后端提供结构化截断计数时，才追加 `截断正文 N 条`；否则使用不带数字的“部分正文按单条预算截断”提示，不能从审计文案反推数量。

完成态应将结果区域标记为：

```text
完整快照复盘
基于任务快照中的 508 / 508 条笔记生成。
```

不能只显示“本地缓存”，因为“本地缓存”没有表达覆盖范围。

### 6.5 失败、部分完成和取消

状态必须分别说明下一步：

- `部分批次失败`：显示失败批次编号和 `重试失败批次`。
- `任务失败`：显示失败原因和 `创建新的快照`。
- `任务已取消`：保留已处理数量；当前实现将取消视为终态，只显示 `创建新的快照`。若未来要支持继续，必须先扩展后端状态机和恢复契约，不能只在 UI 增加“继续任务”。

半截结果不能标记为“完整快照复盘”，也不能写入正式复盘结果区。

## 7. 结果来源标识

页面结果区需要从后端显式覆盖状态推导来源。`promptVersion` 只能标识处理流程，不能单独证明完整覆盖。完整快照复盘必须同时满足：

```text
job.status === completed
job.coverage.fullSnapshot === true
job.processedCount === job.totalCount
job.failedBatchCount === 0
```

页面结果区再根据结果类型展示来源：

| 结果类型 | 标识 | 说明 |
| --- | --- | --- |
| 普通生成 | `快速复盘 · 本次生成` | 最多使用有限样本 |
| 普通缓存 | `快速复盘 · 本地缓存` | 使用有限样本的历史结果 |
| 全量完成 | `完整快照复盘` | 已通过完整覆盖校验 |
| 旧普通缓存 | `快速复盘 · 旧缓存` | 当前笔记变化后暂时回退 |

结果来源说明至少包含：

- 结果类型；
- 最多使用笔记数 / 本地总数（普通复盘）；
- 划线与想法的纳入数；
- 普通复盘的抽样策略、采样版本和章节覆盖数；
- 快照创建时间（全量结果）；
- Provider 模型；
- 完整任务的 `jobId` 或可追溯任务标识。

导出 Markdown 的元数据也应使用相同语义，避免页面显示“完整复盘”而导出文件只写“来源：本地缓存”。

## 8. 持久化读取契约

当前 `get_active_note_synthesis_job` 只返回活动状态，无法在刷新后恢复完成态。不能只增加一个“最近任务”字段，因为活动任务、最近完成任务和最近失败任务可能不是同一条记录。增加只读查询：

```text
get_note_synthesis_job_summary(bookId)
```

建议返回：

```text
activeJob: NoteSynthesisJob | null
latestCompletedJob: NoteSynthesisJob | null
latestTerminalJob: NoteSynthesisJob | null
```

每个任务对象至少包括：

- `status`；
- `sourceSnapshotHash`；
- `totalCount` / `processedCount`；
- `batchCount` / `completedBatchCount` / `failedBatchCount`；
- `coverage`；
- `providerModel` / `providerLabel`；
- `consentConfirmedAt`；
- `createdAt` / `finishedAt` / `updatedAt`；
- `failedBatches`。

完成的 AI 资产引用还应保存 `jobId`，避免“新任务状态 + 旧任务结果”在 UI 中错配。

页面加载时并行读取：

```text
previewNoteSynthesis(bookId)
getNoteSynthesisJobSummary(bookId)
getBookNotesSummaryVariants(bookId)
```

任务区读取优先级（不替代第 15.3 节的模式恢复优先级）：

1. 活动任务；
2. 最近完成任务的完成摘要；
3. 最近失败或取消任务的恢复提示；
4. 无任务时显示创建入口。

双结果读取后由当前模式选择对应结果；页面来源标识必须同时显示为 `快速复盘` 或 `完整快照复盘`。旧 `getLatestBookNotesSummary` 只作为兼容调用，不参与新页面的模式判断。

### 8.1 结果选择与快照过期

快速复盘和完整复盘必须有明确的选择规则：

- 完整复盘是已验证的正式成果；
- 快速复盘是有限样本的临时或补充结果，不覆盖完整复盘；
- 用户刚生成快速复盘时，可以在当前页面查看它，但必须显示 `快速复盘 · 本次生成`；
- 在没有显式 URL 参数或用户主动模式偏好的情况下，刷新页面后默认恢复正式的完整复盘，并在页面提供 `查看快速复盘` 或版本入口；若 URL 明确要求快速模式，不能无提示地切换到完整结果。

全量结果还需要支持快照新旧提示。后端预览返回当前笔记集合哈希，页面只对已完成任务比较该哈希与任务创建时保存的 `sourceSnapshotHash`：

```text
snapshotCreatedAt
snapshotHash
currentSourceHash
isStale
```

当 `isStale = true` 时显示：

```text
当前书籍已有新笔记或修改；本复盘基于旧快照，未包含这些变化。
```

## 9. 前端组件改造

### 9.1 `BookAiSummaryPage`

- 增加 `isFullSnapshotSummary` 派生状态。
- 普通生成按钮显示动态采样数量。
- 结果边界条根据完整/快速来源显示不同文案。
- 加载最近任务，不只加载活动任务。
- 完成任务后提供滚动到结果区的操作。

- 为 `completed` 增加完成摘要和结果操作。
- 完成态不渲染授权控件。
- 失败、取消和部分完成使用明确的恢复动作。
- 将快照统计与任务进度拆成两行，避免窄屏溢出。

### 9.3 结果边界组件

建议抽取 `BookReviewSourceBoundary`，统一处理：

- 快速复盘来源；
- 完整快照复盘来源；
- 旧缓存；
- 待生成。

避免在页面多个位置分别判断 `source` 和 `promptVersion`，减少来源文案漂移。

### 9.4 普通复盘选择摘要

普通复盘的选择摘要应作为后端结果的一部分返回，由页面直接渲染，不在前端重新抽样。建议使用独立的纯函数/服务：

```text
selectQuickReviewNotes(notes, {
  bookId,
  highlightBudget: 80,
  thoughtBudget: 20,
  samplingVersion: "book-review-sampling-v1"
}) -> {
  selectedNotes,
  selectionSummary
}
```

职责边界：

- 后端负责候选过滤、稳定优先级、章节分层、预算分配和输入哈希；
- 前端只展示 `selectionSummary`，不依赖本地数组顺序推断纳入数；
- Prompt 只接收 `selectedNotes`，并将 `selectionSummary` 作为覆盖声明；
- 缓存命中时复用已保存的选择摘要和结果，不重新执行抽样。

这样可以避免不同端（桌面、移动、Web 预览）因为排序或随机数实现差异而生成不同复盘。

## 12. 变更风险与回滚

### 12.1 风险

- 从顺序截取改为分层抽样后，普通复盘的内容会变化，用户可能将差异误认为 Provider 波动；结果来源区必须显示采样版本。
- 将想法预算从当前 80 调整为 20 是输入范围收窄，可能减少少数书籍中想法的覆盖；应先在脱敏样本上比较主题、行动建议和想法引用质量。
- 章节元数据缺失或不稳定时，分层效果会退化为“未分章”分层；不能把章节覆盖数解释为实际章节语义质量。

### 12.2 回滚策略

- 保留旧 `samplingVersion` 的读取和结果展示能力，不删除历史快速复盘；
- 如抽样质量未达门槛，可将默认版本切回旧版本，但仍保留 `selectionSummary` 和 `coverage: sampled`，不能恢复“顺序截取但不标示”的隐式行为；
- 回滚只影响新生成结果，不覆盖已经保存的全量快照复盘。

### 12.3 发布门槛

- 100% 的普通结果都能区分 `available`、`included` 和预算上限；
- 相同输入在桌面端和移动端选择 ID 一致；
- 章节覆盖和想法纳入率不低于顺序基线，且主题质量人工评估无明显退化；
- 新旧缓存不会因缺少采样版本而互相误认；
- 纯随机数、数组下标、当前时间和请求 ID 不得参与选择结果。

## 14. P1.7 快速复盘与完整复盘模式隔离

### 14.1 改造结论

当前页面可以继续作为单本书籍复盘的统一入口，但不应把快速复盘和完整复盘作为两条连续内容流同时展开。两者的输入范围、等待时间、Provider 边界和用户目标不同：

- **快速复盘**：即时生成、有限抽样、本地结果优先，适合先看主题、观点和行动。
- **完整复盘**：固定快照、分批处理、需要显式授权，适合生成可归档的完整成果。

因此采用“同一页面外壳 + 两种明确模式”的方案，不立即拆成两个完全独立页面，也不继续把两个工作流堆叠在同一纵向页面中。

### 14.2 当前 UI 问题证据

截图所示页面同时出现：

- 顶部的“生成快速复盘”“重新生成快速复盘”“复制完整复盘”“导出书籍复盘”；
- 完整复盘的笔记总数、批次预估、授权复选框和快照创建入口；
- 完整任务状态、整理状态、快速复盘来源边界和复盘结果内容。

这会造成以下歧义：

1. 用户无法立即判断当前页面的主任务是“先看快速结果”还是“开始完整任务”。
2. 完整任务卡出现在快速结果之前，用户容易把任务准备信息误认为复盘结果。
3. `快速复盘`、`完整复盘`、`完整快照复盘` 和 `复制完整复盘` 命名相近，但没有明显的模式边界。
4. 顶部操作过多，生成、刷新、复制和导出同时争夺主按钮层级。
5. 快速结果和完整结果共享同一个结果区域时，来源标签、整理状态和结果内容可能被误读为同一版本。

### 14.3 信息架构目标

- 页面首次进入时只呈现一个明确的当前模式。
- 快速模式优先帮助用户获得即时结果；完整模式优先帮助用户完成任务。
- 同一时刻只展示当前模式的主要结果和主要操作，不同时展开两套结果内容。
- 完整任务的授权、详细进度、失败批次和取消控件只在完整模式出现；另一模式最多显示一条可切换的轻量状态入口。
- 快速复盘的抽样范围和完整复盘的快照覆盖量始终可见，但不重复解释相同边界。
- 切换模式只改变展示上下文，不自动重新生成、不重复调用 Provider。

### 14.4 页面结构

```text
《书名》书籍复盘                         状态
读取已保存结果；生成时使用当前书笔记

[快速复盘（抽样）] [完整复盘（快照）]

快速模式
  覆盖说明：最多使用 100 / 577 条，按章节分层抽样
  [生成快速复盘] 或 [重新生成快速复盘]
  概览、关键观点、关注点、行动、摘录、复盘问题
  [标记已整理]
  [进入完整复盘]

完整模式
  当前快照：577 条笔记，预计 34 个批次
  授权、创建快照、开始发送、进度、失败重试、取消
  完成后展示完整复盘结果和覆盖量
  [复制完整复盘] [导出完整复盘]
```

模式名称必须带范围语义：

- `快速复盘（抽样）`，避免用户误解为完整总结；
- `完整复盘（快照）`，避免把“完整”误解为不受快照和正文预算约束。

### 14.5 模式选择规则

```text
首次进入且没有正式完整结果 -> 快速模式
用户点击“进入完整复盘”或“创建完整复盘任务” -> 完整模式
无显式 URL 参数且存在活动完整任务 -> 自动恢复完整模式
完整任务已完成且用户从任务卡查看结果 -> 完整模式
刷新页面且存在已验证完整结果 -> 默认恢复完整模式
无活动任务且用户手动切换 -> 保留用户选择，不触发生成
```

建议将模式写入 URL 查询参数或按书籍保存轻量偏好：

```text
?reviewMode=quick
?reviewMode=full
```

这样刷新、浏览器返回和完成任务后的“查看完整复盘”都不会丢失上下文。模式参数不应改变后端输入哈希或缓存键。

### 14.6 快速模式行为

快速模式只保留：

- 当前快速结果或空态；
- `生成快速复盘` / `重新生成快速复盘` 一个主生成操作；
- 抽样数量、划线/想法预算和章节覆盖说明；
- 结果复制、导出等次级操作；
- 进入完整复盘的轻量入口。

快速模式不展开完整任务的授权复选框、批次明细、失败批次或取消按钮；若任务已存在，只显示轻量状态入口。完整任务入口使用短说明：

```text
想覆盖当前书的全部可处理笔记？进入完整复盘。
```

快速结果的 `ReviewCompletionStrip` 放在结果末尾，不插入完整任务说明中间。

### 14.7 完整模式行为

完整模式只保留：

- 快照统计和授权说明；
- 创建快照、开始发送并归纳、继续归纳、重试失败批次、取消任务；
- 处理数量、批次、模型、完成时间和旧快照提示；
- 完成后查看、复制和导出完整结果。

完整模式不展示快速复盘结果正文，也不展示“生成快速复盘”按钮。用户需要快速结果时，通过模式切换返回快速模式，不在完整模式下追加第二个结果区。

创建快照和发送正文仍是两个明确动作：

1. `创建本地快照`：只固定本次任务输入，不发送笔记正文。
2. `开始发送并归纳`：在用户确认后，才把快照中的原始笔记正文发送给 Provider。

完成态隐藏授权复选框，不再显示继续调用 Provider 的误导性入口。

### 14.8 顶部操作层级

顶部 Hero 只保留当前模式的一个主操作：

| 模式 | 主操作 | 次级操作 |
| --- | --- | --- |
| 快速 | 生成快速复盘 / 重新生成快速复盘 | 进入完整复盘、更多操作 |
| 完整 | 创建快照 / 开始发送并归纳 / 继续归纳 | 重试、取消、更多操作 |
| 完整完成 | 查看完整结果 | 复制、导出、创建新快照 |

复制和导出不应与生成操作并列为四个同权按钮；可放入当前结果区底部或“更多”菜单。移动端应保证主操作在首屏可见，次级操作可折叠。

### 14.9 组件拆分

建议在 `BookAiSummaryPage` 内增加以下边界：

- `ReviewModeTabs`：只负责模式切换、键盘操作和当前模式语义；
- `QuickReviewPanel`：快速生成、覆盖说明、快速结果和整理状态；
- `FullReviewPanel`：快照授权、任务卡、进度和完整结果；
- `BookReviewSourceBoundary`：统一展示当前模式的来源、覆盖和新鲜度；
- `ReviewResultActions`：复制、导出、查看结果等与结果绑定的操作。

`NoteSynthesisJobCard` 只在完整模式挂载。切换模式不应卸载后台任务状态查询；活动任务仍可在切回完整模式时恢复。

### 14.10 数据与状态契约

前端增加轻量展示状态，不改变后端生成契约：

```ts
type BookReviewMode = "quick" | "full";

type BookReviewViewState = {
  mode: BookReviewMode;
  quickResult?: BookAiSummaryResponse;
  fullJob?: NoteSynthesisJob;
  fullResult?: BookAiSummaryResponse;
  sourceBoundary: BookReviewSourceBoundary;
};
```

结果选择必须保持以下优先级：

1. 完整任务通过完整覆盖校验且用户处于完整模式时，展示完整结果；
2. 快速模式展示快速结果或快速空态；
3. 不把快速结果填充到完整模式的结果区；
4. 不把活动任务的进度与旧任务结果拼接成一个结果；
5. 快照过期只影响完整结果状态，不把完整结果降级成快速结果。

### 14.11 响应式与视觉规则

- 桌面端模式切换使用紧凑的 segmented control，不新增两个大型并列卡片。
- 移动端模式切换占满可用宽度，两个标签可完整显示，不出现横向滚动。
- 快速模式和完整模式使用不同的状态色与副标题，但沿用现有设计系统，不新增装饰性背景。
- 同一屏最多出现一个主要生成按钮和一个状态说明区。
- 长书名、Provider 名称、授权文案和批次统计允许换行，不撑宽按钮或造成横向溢出。
- “来源与覆盖范围”作为一个可折叠的辅助区域，避免 Hero、边界条和结果卡重复写同一段说明。

- 不改变现有生成、缓存写入和任务执行语义；按第 15.1、15.2 节增加只读结果读取和当前结果绑定参数。

#### P1.7.2：条件渲染与操作降噪

- 快速模式只渲染快速结果及其操作；
- 完整模式只渲染快照任务及完整结果；
- 顶部主操作按模式切换，复制和导出下沉到结果操作区；
- 完整任务进行中时，快速结果不再与任务卡同屏展开。

#### P1.7.3：来源边界与结果恢复

- 抽取 `BookReviewSourceBoundary`，统一快速/完整/旧快照文案；
- “查看完整复盘”改为切换到完整模式，不仅滚动页面；
- 刷新和浏览器返回后恢复正确模式及对应结果；
- 保留旧缓存、旧消息和历史任务兼容显示。

#### P1.7.4：响应式验收

- 验证 1280px、768px 和 390px 视口；
- 验证模式切换、活动任务恢复、完成结果查看和快照过期提示；
- 确认无水平溢出、按钮同权级过多或结果来源混淆。

### 14.13 验收标准

- 首次进入页面时，用户能在 3 秒内辨认当前是快速模式还是完整模式；
- 快速模式首屏不出现完整任务授权、批次明细和失败重试控件；活动任务只允许显示聚合状态入口；
- 完整模式首屏不出现快速结果正文和快速生成按钮；
- 页面同一时刻只渲染一套主要结果内容；
- 快速模式明确显示抽样数量和“不代表全量覆盖”；
- 完整模式明确显示快照数量、已处理数量、批次和 Provider；
- “创建本地快照”和“开始发送并归纳”的授权边界保持不变；
- 完整任务完成后，查看结果会切换模式，且刷新后仍能恢复完整结果；
- 切换模式不会触发额外 Provider 调用；
- 桌面和移动端无横向溢出，长文案不会遮挡前后内容；
- `BookAiSummaryPage`、模式切换、结果来源和任务恢复的定向测试全部通过；完整套件的权限 schema 失败需单独处理。

### 14.14 本次改造的非目标

- 不改变快速复盘的 80 条划线 + 20 条想法预算和稳定抽样算法；
- 不改变完整快照的分批、合并、失败重试和授权机制；
- 不新增自动生成、自动同步或自动发送原始笔记；
- 不要求立即拆分成两个独立路由；
- 不把完整复盘结果与快速复盘结果合并为一个无法区分来源的“最终结果”。

当前结论：现有基础生成链路和任务状态能力可以复用，但页面需要先完成模式隔离，才能避免快速复盘内容与完整复盘任务在同一纵向流程中互相挤压。

## 15. 评审补充与边界修正

本节补齐 P1.7 实施前必须明确的接口和状态边界。它们不是新增产品功能，而是为了保证“快速复盘”和“完整复盘”在同一页面内仍然可区分、可恢复、可追溯。

### 15.1 双结果读取契约

当前后端 `get_latest_book_notes_summary` 只返回一个按优先级选出的结果（通常是完整结果，否则快速结果）。该契约无法支撑前端同时知道 `quickResult` 和 `fullResult` 是否存在，模式切换也可能读到错误来源。

实施时必须增加以下一种最小能力：

- 新增 `getBookNotesSummaryVariants(bookId)`，返回 `quick`、`full` 两个可空结果；或
- 给现有读取接口增加明确的 `reviewKind` 参数，并分别读取 `quick` 与 `full`。

原有 `get_latest_book_notes_summary` 的“完整优先、否则快速”语义可继续服务旧调用方，但不能让新复盘页通过这一个结果猜测两种模式；若采用参数扩展，应保留无参数调用的兼容行为。

结果元数据至少应包含：

| 字段 | 用途 |
| --- | --- |
| `reviewKind` | 明确是 `quick` 还是 `full` |
| `inputHash` | 绑定本次结果使用的笔记集合 |
| `jobId` | 将完整结果绑定到已完成的全量任务 |
| `sourceSnapshotHash` | 校验完整结果对应的快照 |
| `coveredNoteCount` / `totalNoteCount` | 展示覆盖范围，避免把抽样结果说成全量 |
| `generatedAt` | 展示新鲜度和处理时间 |

兼容规则：旧 `book-notes-summary-v3` 归类为快速结果；`book-notes-summary-full-v1` 只有能够绑定已完成任务和快照时，才可以标记为完整结果，否则只能按历史结果展示，不能宣称覆盖全量。该补充不改变 Provider 的生成逻辑，只增加结果读取和来源标识能力。

上述元数据是前端读取契约的最低信息集合，不要求全部重复写入 `ai_outputs`。完整结果的 `jobId`、`sourceSnapshotHash` 和覆盖报告可以通过 `note_synthesis_jobs.result_*` 与结果引用关联得到；只有无法可靠关联时才需要扩展持久化字段。接口应在返回前完成关联和一致性校验，避免把数据库内部的多次查询暴露给页面。

### 15.2 复制、导出与反馈必须绑定当前结果

- 复制和导出请求必须携带当前结果引用，至少包括 `bookId + reviewKind + inputHash`；完整结果还应带 `jobId` 或 `sourceSnapshotHash`。
- 后端导出不得再次按“最新结果”查询，否则用户在完整/快速模式切换后可能导出另一种结果。
- 反馈应按 `bookId + inputHash`（或不可变 `resultId`）隔离，不能只按书籍保存；快速结果的反馈不应污染完整结果。
- 当前模式没有结果时，复制、导出和反馈入口应禁用或隐藏，并显示对应空态，不得回退到另一模式的正文。

### 15.3 模式恢复优先级

页面只允许一个最终模式状态源，建议按以下优先级解析：

1. 有效的显式 URL 参数（例如 `?reviewMode=quick|full`）；
2. 当前书籍存在的活动完整任务；
3. 用户最近一次对该书籍主动选择的模式偏好；
4. 只有完整结果而没有快速结果时选择完整模式；
5. 其余情况默认快速模式。

URL 参数是一次性导航意图，不应与本地偏好同时竞争；只有用户主动切换模式时才更新按书籍保存的偏好。无效参数应忽略并回落到后续规则，不能把用户偏好写坏。

### 15.4 非当前模式的后台任务提示

快速模式不展开完整任务卡、授权文案和批次明细，但不能让完整任务完全不可见。建议在结果区上方显示一条按状态映射的轻量入口：

`完整复盘进行中 · 已处理 x/y · 查看任务`

`partial` 应显示为“完整复盘部分失败 · 重试失败批次”，`failed/cancelled` 应显示为“完整复盘未完成 · 查看任务”。点击后切换到完整模式；任务完成后不要自动抢占当前模式，只显示“完整复盘已完成 · 查看结果”的入口。任务失败、过期或取消应保留对应状态和重试/创建新快照动作，且不能把失败任务当作完整结果。

反向切换也要保留状态：完整模式下若快速复盘正在生成，只显示“快速复盘生成中 · 查看状态”的轻量入口，不重复发起请求；切回快速模式后继续显示原有生成状态。两种轻量入口都不能把另一模式的正文或任务授权控件带入当前模式。

### 15.5 加载、错误与异步竞态隔离

- 快速生成和完整任务使用相互独立的 `loading`、`error`、`lastRequestId` 状态；快速请求失败不应覆盖完整任务状态，反之亦然。
- 每个异步响应都要校验 `bookId + reviewKind + requestId`，旧书籍、旧模式或旧请求的响应直接丢弃。
- 模式切换本身只改变展示，不调用 Provider；只有点击生成、创建快照或重试时才发起写操作。
- 结果刷新、任务轮询和浏览器返回同时发生时，保持当前模式和结果引用一致，不能短暂显示另一模式正文后再切回。
- 用户可以明确点击生成快速复盘或开始完整发送，两个请求即使并行也必须分别记录状态；不因另一模式有活动任务就自动生成，也不把一个模式的限流、取消或失败映射成另一个模式的错误。
- 取消完整任务只取消该快照任务；快速复盘的一次性请求若不支持取消，应继续独立显示完成或失败，不提供会误取消完整任务的共用按钮。
- 没有可处理笔记时，两种模式都显示空态并禁用生成/创建快照；不能用旧缓存的笔记数量替代当前可用数。
- 没有聊天 Provider 凭据时，快速模式提供“前往设置”动作；完整模式仍可创建本地快照，但“开始发送并归纳”必须禁用并说明需要恢复凭据。
- 快速生成失败时可以保留经过明确标记的旧快速缓存；完整任务失败、取消或过期时不能把旧快速缓存显示在完整结果区。

### 15.6 “标记已整理”的状态语义

`organizeStatus` 是书籍级状态，不属于快速或完整模式。页面只保留一个“标记已整理/已整理”入口，在两种模式下复用；该动作表示用户确认吸收本书复盘成果，不代表某一种生成路径已完成。若产品未来需要记录“基于哪份结果整理”，应新增独立的 `organizedFromResultId`，不能复用模式字段偷渡语义。

### 15.7 组件拆分的控制范围

一次性拆出五个组件会扩大改动面，也可能把尚未稳定的接口固化。建议分阶段执行：

1. 先在 `BookAiSummaryPage` 内完成模式状态、条件渲染和结果引用绑定；
2. 出现真实重复后，再抽取 `BookReviewSourceBoundary` 和 `ReviewResultActions` 等稳定边界；
3. `ReviewModeTabs` 可独立抽取，但 `QuickReviewPanel`、`FullReviewPanel` 是否拆分以测试和职责清晰度为准，不作为验收前置条件。

`NoteSynthesisJobCard` 只在完整模式渲染；任务查询和轮询状态应由页面级状态持有，切换到快速模式时不停止查询，切回完整模式时可恢复同一任务。

### 15.8 无障碍与导航一致性

- 模式控件使用 `tablist`/`tab`/`tabpanel`，或语义等价的单选组；当前项提供 `aria-selected`，结果面板通过 `aria-controls` 关联。
- 支持键盘方向键切换，焦点环清晰；切换后将焦点移到当前模式标题或结果区域，不让焦点落在已隐藏的控件上。
- 浏览器前进/后退、刷新和深链接打开后，URL 标签、选中状态和结果正文必须一致。
- 状态色不能作为唯一信息来源，快速/完整、进行中/失败/完成都要有可读文本。

### 15.9 验收与测试矩阵补充

除第 14.13 节外，至少覆盖以下场景：

| 场景 | 必须验证 |
| --- | --- |
| 快速、完整结果同时存在 | 两种模式分别显示各自正文、数量和来源 |
| 模式切换后复制/导出 | 导出的结果与当前 `reviewKind` 和 `inputHash` 一致 |
| 完整任务后台运行 | 快速模式只显示轻量入口，任务完成不强制跳转 |
| 完成、过期、失败、取消 | 每种状态均有正确文案和可用动作 |
| 部分批次失败 | 显示“部分失败”和重试失败批次，不持续显示为进行中或无条件轮询 |
| URL、活动任务、用户偏好 | 按 15.3 的优先级恢复，且无效 URL 不污染偏好 |
| 反馈隔离 | 快速与完整结果的反馈互不串联 |
| 并发与旧响应 | 切书、切模式、重复点击不会覆盖当前结果 |
| 视口与辅助技术 | 390/768/1280px 无溢出，键盘和读屏状态可用 |
| 旧结果兼容 | 无完整任务引用的旧结果不被错误标记为全量 |
| Provider 设置变化 | 继续/重试时不静默切换 Provider，给出恢复原配置或创建新快照的动作 |
| 重复启动 | 双击或并发启动只保留一个活动任务，不重置授权和进度 |
| 结果引用不一致 | 结果行与任务引用不匹配时按不可用处理，不回退到另一模式 |
| 结果操作命名 | 快速结果只出现快速复制/导出，完整结果只出现完整复制/导出，历史或空态不误启用操作 |
| 另一模式正在生成 | 当前模式只显示轻量状态入口，不重复调用、不展示另一模式正文 |
| 页面卸载/切书 | 只停止旧页面轮询，不取消任务；旧响应不能写入新书或新页面 |
| 应用重启恢复 | 复用原 `jobId` 和快照，按持久状态显示待继续/终态，不自动重复发送 |
| 快速结果过期 | 请求期间笔记变化时标记“生成时笔记”，不自动重新调用 Provider，重新生成失败仍保留旧结果 |
| 无笔记/无凭据 | 生成与授权动作按 15.5 的空态和设置引导处理 |
| 章节或分批版本变化 | 旧完整结果显示过期或不可复用，不因笔记数量相同而误判为当前结果 |

### 15.10 任务授权、Provider 快照与幂等

- 完整任务创建时已经记录 Provider 地址标识、Provider 名称、模型和授权确认时间。任务卡应展示任务创建时的这些值，不随设置页当前值变化。
- 继续或重试前若当前 Provider 地址或模型与任务创建时不一致，后端会拒绝继续；UI 应显示“恢复任务创建时的 Provider/模型”或“创建新的快照”，不能静默使用当前配置重新发送原始笔记。
- 当前契约允许用户在创建本地快照前确认“后续开始完整复盘时会发送正文”，并记录 `consentConfirmedAt`；创建快照本身不发送正文，后续“开始发送并归纳”才是网络动作。轮询、切换模式和读取结果不应重复弹出授权确认；若要把确认延后到实际发送，必须同步修改任务接口，不能只改 UI 文案。
- 同一本书已有活动任务时，启动命令返回已有任务而不是创建第二条任务。前端应锁定重复点击、保留原有轮询和进度，不能把 `created: false` 当作新任务清空状态。
- 操作按钮必须服从任务状态机：`queued/snapshotting/batching/summarizing/merging` 才是活动执行状态；`partial` 表示等待用户重试失败批次，不持续轮询；`failed`、`cancelled` 是终态，不能显示“继续任务”。

### 15.11 快照、索引与兼容迁移边界

- 完整复盘的来源真相是 `note_synthesis_job_items` 中的不可变笔记快照，不是 FTS、向量索引或当前页面加载的笔记数组。索引重建失败不能改变快照哈希或已完成结果的来源判断。
- 快速复盘使用当前笔记集合的 `available/included` 统计；完整复盘使用任务 `coverage` 和快照数量。两套数字不得相加、互相覆盖或用检索命中数替代快照覆盖数。
- 笔记新增、修改或删除后，已完成的完整结果仍可作为历史资产查看，但必须显示旧快照/来源时间；不能自动把快速结果拼接进完整结果，也不能继续宣称它覆盖当前笔记集合。
- 首版不做历史数据批量迁移：旧 `book-notes-summary-v3` 直接映射为快速结果；没有可验证完成任务引用的旧全量候选只能标记为“历史结果，来源未验证”，不能进入“完整复盘”正式结果区。
- 读取接口必须校验结果行的 `feature + promptVersion + inputHash` 与任务结果引用完全一致。任何一项不一致都按“完整结果不可用”处理并给出创建新快照入口，不回退到快速正文冒充完整结果。
- `sourceSnapshotHash` 必须覆盖会影响分批或归纳的字段，至少包括稳定文档 ID、笔记类型、章节键、原始内容哈希、按单条上限截断后的正文和审计状态；章节归属变化也应触发旧快照提示。
- 完整结果的 `inputHash` 必须同时绑定来源快照、批次 Prompt 版本、合并 Prompt 版本和分批算法版本。版本变化时不能只因笔记集合相同就复用旧正式结果；这些内部版本可由后端校验，不必全部暴露为 UI 文案。

### 15.12 单条正文上限、批次预算与覆盖语义

- `8,000` 字符是单条快照笔记正文上限，`12,000` 字符是单批输入预算；二者都不是整本书的总字符上限。`508 条 / 111 批` 是完成归一化、去重、单条截断和稳定分批后的任务估算。
- 完整复盘的 `totalCount` 是快照项目数；`processedCount` 表示项目已经有处理或审计结论，包含空正文、重复正文等跳过项，并不等于实际发送给 Provider 的正文条数。
- 单条正文被截断不会减少笔记项目覆盖数，只会降低该项目的正文完整度。UI 应同时区分“覆盖了多少项目”和“有多少项目被跳过/截断”，不能用字符数替代笔记数。
- 完整结果中的 `sourceStats.includedHighlightCount/includedThoughtCount` 若按快照项目聚合，可能包含被审计跳过的项目；结果来源区应以任务 `coverage` 和跳过统计为准，不能把 `included*` 直接当作 Provider 实际发送条数。
- 向量/FTS 索引可以使用自己的规范化、分块和字符预算；它是检索派生数据，不参与完整任务的快照覆盖判断，也不会因为单条 8,000 字符上限而与全量复盘冲突。
- `estimatedCharCount` 当前按截断后的快照正文计算，UI 应标注为“快照正文字符估算（已按单条上限）”；若未来需要展示原始正文总字符数，必须新增独立统计字段。

### 15.13 截断统计的最小契约

当前任务接口的 `coverage` 没有 `truncatedCount`，而截断原因只保存在任务项审计原因中。P1 不应直接承诺显示 `截断正文 N 条`，除非先满足以下任一条件：

- 后端增加结构化的可选 `truncatedCount`（必要时同时提供 `providerSentCount`）；或
- 任务项提供结构化截断标记，接口在服务层聚合计数。

不能通过解析本地化的 `auditReason` 文案来计算数字。若暂不增加该契约，完成态只显示已有的空正文/重复计数，并使用不带数字的“部分正文按单条预算截断”提示；这不会影响 `fullSnapshot` 的项目覆盖校验。

### 15.14 过度设计排除项

本次补充不要求新增独立路由、第三套结果存储、自动后台生成完整复盘、向量库查询链路改造或历史数据一次性迁移。第一阶段只需让现有两条生成路径拥有可区分的结果引用和稳定的页面状态；只有在读取契约稳定后，才评估是否需要更细的历史版本管理。

### 15.15 本轮审查遗漏与控制项

以下边界属于模式隔离能够正常上线的最低控制项；它们不是新增复盘能力，也不要求引入新的任务中心。

| 关注点 | 本期必须明确 | 暂不扩展 |
| --- | --- | --- |
| 网络隐私 | Provider 请求、错误、日志、诊断事件和 toast 不得写入原始笔记正文或完整模型输出；错误使用可展示的错误码/脱敏摘要，结果正文只通过结果引用读取 | 不新增通用内容脱敏平台 |
| Provider 限流与成本 | 开始发送前展示笔记数、预计批次、Provider/模型；重试只发送失败批次，不因切换模式或刷新重复发送；没有计费元数据时不得伪造金额或耗时承诺 | 不在本期实现跨 Provider 价格比较或自动择优 |
| 应用重启/异常退出 | 页面重新打开先读取任务持久状态，再决定轮询、继续或终态展示；`partial`、`failed`、`cancelled` 不因本地计时器显示为进行中，终态不继续轮询 | 不新增后台守护进程或系统级队列 |
| 任务与结果生命周期 | 书籍被删除、快照结果无法关联或结果引用失效时，显示“历史结果不可用/创建新快照”，不能回退到另一模式正文；清理策略由现有本地数据策略决定 | 不在本期设计跨设备同步、云端保留期或批量清理 |
| 观测与排障 | 记录 `bookId`、`jobId`、`reviewKind`、状态和错误码等结构化元数据，禁止记录正文；同一请求的重试和取消事件应可关联 | 不要求接入新的远程分析平台 |
| 文案与统计 | 所有数量来自结构化字段，使用本地化只读文案；不能从 `auditReason`、按钮文字或颜色反推覆盖/截断数量 | 不新增第三套统计口径 |

启动前后还需保持以下顺序：

1. 先校验书籍、凭据、Provider 快照和当前任务幂等状态；
2. 再创建或读取不可变快照；
3. 只有用户明确点击发送后才进入 Provider 调用；
4. 每个批次完成后持久化状态，再允许页面刷新或重启恢复；
5. 结果发布前再次校验任务、快照和结果引用，校验失败时宁可显示不可用，也不能降级为另一模式结果。

若现有接口无法提供上述结构化状态，应先补齐接口契约再改 UI；不得用前端定时器、字符串解析或“最新结果”兜底来模拟这些状态。

### 15.16 新旧客户端与接口发布顺序

模式隔离会同时依赖新的双结果读取和结果绑定参数，不能把前端和后端作为一次不可回滚的同步发布。采用向后兼容的两阶段顺序：

1. **先发布只读接口**：增加双结果读取、结果引用校验和当前 `reviewKind` 参数；保留无参数的 `get_latest_book_notes_summary`，继续服务旧页面、导出和历史调用方。
2. **再发布模式 UI**：新页面只有在拿到明确的 `quick`/`full` 结果或结构化“不支持/不可验证”状态后才渲染对应模式；不根据旧接口返回的单个结果猜测覆盖范围。
3. **稳定后再收紧旧调用**：统计确认新页面不再依赖旧接口后，才评估将旧接口降为兼容层；不删除旧结果、不重写历史 `inputHash`，也不在发布过程中批量迁移数据。

新客户端遇到旧后端或旧数据时，必须按以下规则处理：

- 双结果接口不存在、字段形状不完整或结果关联失败：显示“当前版本无法验证快速/完整来源，请更新应用或创建新快照”，并禁止把单一结果标记为完整快照复盘；
- 只能读到旧 `book-notes-summary-v3`：最多作为“快速复盘 · 历史结果”只读展示；复制可以基于已读正文执行，导出只有在后端支持当前结果引用时才启用，否则应禁用并提示兼容限制，不能填充完整模式；
- 只能读到 `book-notes-summary-full-v1` 但缺少任务、快照或覆盖校验：显示“历史结果，来源未验证”，不能提供完整覆盖文案和完整结果操作；
- 后端返回未知的 `reviewKind`、任务状态或覆盖字段：按不可用处理并记录结构化错误，不静默降级到另一模式正文。

旧客户端连接新后端时，仍可继续使用“完整优先、否则快速”的兼容读取语义；这不代表旧客户端已经具备模式隔离能力。回滚 UI 时只回退页面展示和入口，不回滚已经创建的快照、任务状态或结果引用；新后端保留的兼容接口应继续阻止旧结果被误标为全量。

发布验收至少增加四组组合：

| 客户端 | 后端/数据 | 预期 |
| --- | --- | --- |
| 旧 | 新 | 旧页面可用，仍按旧优先级读取；不影响新任务和新结果写入 |
| 新 | 新 | 快速/完整双结果、任务和导出均按引用隔离 |
| 新 | 旧 | 不伪造覆盖范围；显示兼容提示或只读历史快速结果 |
| 新 | 新但历史数据不完整 | 历史结果可见但标记来源未验证，不能进入完整正式结果区 |

若工程已有运行时功能开关，可将模式 UI 作为可关闭的 `bookReviewModeIsolation` 能力；若没有现成功能开关，不应为了本次改造新增远程配置系统，直接依赖接口能力和版本化发布顺序即可。

### 15.17 结果操作命名、权限与空态

结果操作必须从当前显示的不可变结果引用派生，不能沿用页面上的历史按钮状态，也不能在没有当前结果时再次查询“最新结果”兜底。建议按以下矩阵实现：

| 当前上下文 | 来源标签 | 可用操作 | 禁止行为 |
| --- | --- | --- | --- |
| 快速结果已生成或命中缓存 | `快速复盘 · 本次生成/本地缓存/历史结果` | `复制快速复盘`、`导出快速复盘`、反馈 | 不得显示或调用“复制完整复盘” |
| 完整任务已验证完成 | `完整快照复盘` | `复制完整复盘`、`导出完整复盘`、反馈、查看覆盖详情 | 不得把快速结果正文拼入导出内容 |
| 完整结果已完成但快照过期 | `完整快照复盘 · 旧快照` | 可复制/导出，但按钮和导出元数据必须注明“旧快照” | 不得宣称覆盖当前笔记集合，不得静默刷新为快速结果 |
| 结果存在但来源未验证 | `历史结果 · 来源未验证` | 仅在结果引用可追溯时允许复制；导出和反馈按接口能力禁用或明确标注兼容限制 | 不得进入完整正式结果区 |
| 当前模式无结果、任务未完成或只有另一模式结果 | 对应空态或轻量任务状态 | 无复制、导出和反馈；可提供切换模式/查看任务 | 不得回退读取另一模式正文 |

按钮可以在窄屏使用“复制当前复盘”“导出当前复盘”等通用短文案，但必须同时满足：

- 来源边界在同一可见区域内明确写出 `快速` 或 `完整快照`；
- 无障碍名称包含实际模式，例如“复制快速复盘”；
- 请求仍携带 `reviewKind + inputHash`，完整结果另带 `jobId` 或 `sourceSnapshotHash`；
- 操作完成后的 toast、导出文件名和 Markdown 元数据使用同一来源名称。

当用户从另一模式的轻量入口切换过来时，只改变模式和焦点位置，不自动触发复制、导出、反馈或 Provider 调用。这样可以避免用户点击“查看任务”后，页面仍持有上一模式的结果操作，造成复制/导出内容与当前视觉上下文不一致。

### 15.18 页面生命周期与任务所有权

页面展示状态和完整任务执行状态必须分离。页面卸载只影响前端订阅和轮询，不改变任务本身；只有用户明确点击“取消任务”才调用取消命令。

| 生命周期事件 | 前端动作 | 禁止行为 |
| --- | --- | --- |
| 快速/完整模式切换 | 保留两套结果引用和任务状态；暂停详细任务卡展示，切回时恢复同一任务 | 不取消任务、不重新创建快照、不重复调用 Provider |
| 切换到另一书籍 | 停止旧书籍的轮询并清空页面局部状态；所有异步响应校验 `bookId` 后再写入 | 不把旧书结果、进度或错误写入新书页面 |
| 离开复盘路由 | 取消前端定时器和订阅，但保留已创建任务；返回页面后重新读取持久状态 | 不因组件卸载自动调用取消、不把“离开页面”当作用户撤回授权 |
| 用户明确取消 | 调用取消命令，收到持久化终态后停止轮询并显示已取消 | 网络请求失败时不能假设任务已取消，也不能直接清空任务记录 |
| 应用重新打开 | 先读取活动/终态摘要；仅对可确认仍在执行的状态轮询，其他状态显示“已保存进度/待继续”或终态动作 | 不因本地旧计时器显示“正在进行”，不自动续跑 Provider 调用 |

任务执行不依赖 `BookAiSummaryPage` 是否仍挂载。若当前运行时无法提供“后台执行心跳”或执行者标识，UI 不得把数据库中的 `summarizing/merging` 单独解释为实时进行中；可以显示“已保存进度，重新打开后可继续”，由用户明确触发继续或重试。该约束不要求新增后台守护进程，但要求状态文案与可观测事实一致。

应用重启后的恢复仍须复用原 `jobId`、`sourceSnapshotHash`、Provider 快照和已完成批次；不能通过创建新任务来“恢复”，也不能把恢复失败伪装成新任务失败。恢复动作完成前，快速模式只显示一条轻量入口，完整模式显示可操作的恢复状态和明确错误。

### 15.19 预览到创建快照的竞态

完整复盘卡片中的笔记数量、字符估算和批次数来自预览读取，只代表读取时的估算，不是已经锁定的输入。用户查看预览后，笔记可能被新增、修改、删除或重新归一化；创建任务时必须以服务端重新建立且与任务写入一致的快照为准。

- `start_note_synthesis` 应在一次不可被前端打断的服务端创建流程中重新读取、归一化、去重、截断、分批并写入 `note_synthesis_jobs`；数据库事务边界允许时保持读取与写入的一致性，至少保证返回值与已写入任务完全一致。接口返回实际的 `sourceSnapshotHash`、`totalCount`、类型计数、批次和字符估算；前端不得把创建前的预览数字复制到任务卡。
- 若创建返回的来源哈希或数量与预览不同，任务卡立即替换为实际快照统计，并显示“笔记在预览后发生变化，已按创建时数据建立快照”；不能继续显示旧的 `508 / 111` 估算，也不能把差异误报成任务失败。
- 用户在预览阶段确认的是“后续会向指定 Provider 发送当前快照正文”这一动作和 Provider 身份，不是对某个固定数量的永久授权。实际发送前仍应在完整模式显示最终快照数量、批次和 Provider；如果产品要求对输入范围逐次确认，应在“开始发送并归纳”前增加一次基于最终快照的确认，而不是只依赖旧的预览复选框。
- 如果创建请求因幂等性返回已有任务（`created: false`），前端必须采用已有任务的快照和 Provider 信息，不得用本次预览覆盖原任务统计，也不得重新弹出一份看似新的授权确认。
- 创建快照成功后到用户点击发送前，笔记继续变化不应修改该任务；页面应显示“快照已固定”，变化只在后续当前来源哈希比较中体现为旧快照。

验收至少覆盖：预览后新增笔记、预览后删除笔记、预览后正文修改、预览过期但返回已有活动任务，以及创建快照后源笔记再次变化。所有场景都必须满足“任务快照统计等于实际任务输入，快速结果不被替换到完整任务中”。

### 15.20 快速复盘请求与笔记变化竞态

快速复盘没有不可变全量快照，但每次请求仍必须绑定本次实际选中的笔记集合。请求开始后笔记变化时，不能把返回结果无条件标成“当前最新复盘”。

- 快速请求的 `inputHash` 必须覆盖实际候选集合、稳定采样结果、正文内容哈希、章节键、采样版本和预算；返回的 `selectionSummary` 以请求时实际纳入数为准，不能由页面根据返回时的当前笔记数组重新计算。
- 请求完成后，页面可重新读取当前笔记来源哈希；若当前来源与结果输入不一致，结果仍可展示，但来源文案应为“快速复盘 · 生成时笔记”，并提示“笔记已有变化，重新生成可纳入最新内容”。不应自动发起第二次 Provider 请求。
- 快速结果过期只表示它不是当前笔记集合的最新抽样，不等同于完整快照的 `isStale`，也不能因此把快速结果移动到完整模式或删除用户刚生成的结果。
- 用户点击重新生成时，旧快速结果在新请求完成前继续作为历史结果显示并保留 `inputHash`；新请求失败时可恢复显示旧结果，但必须同时显示失败原因和重新生成入口，不能覆盖旧结果的来源元数据。
- 切书、切模式或重复点击后，响应必须校验 `bookId + reviewKind + requestId`；旧响应只能丢弃，不能更新当前快速结果、错误、选择摘要或反馈状态。

快速模式的验收至少覆盖：请求期间新增笔记、请求期间修改正文、请求期间删除候选、旧结果存在时重新生成失败，以及快速请求与完整任务并行。所有场景都必须满足“结果正文、选择摘要、`inputHash` 和来源文案来自同一次快速请求”。

## 16. P1.8 生成成功态 UI 收敛改造

### 16.1 现状与问题证据

P1.7 完成模式隔离后，快速复盘生成成功态已经能够正确表达结果来源，但截图显示首屏仍有明显的操作和信息堆叠：

- Hero 同时显示禁用的“生成快速复盘”、可用的“重新生成快速复盘”、复制和导出四个按钮；成功后仍保留一个已经没有实际用途的禁用主按钮。
- 右上角状态只写“已生成”，没有明确说明是快速复盘还是完整复盘；用户必须继续阅读来源边界才能确认当前结果类型。
- `最多使用 94 / 422 条`、`快速复盘 · 本次手动生成`、`来自有限样本，不代表全量覆盖` 都在重复表达同一来源边界。
- 模式切换、进入完整复盘卡片、来源边界卡片和整理状态卡片连续占据结果区上方，真正的“概览”在首屏只露出很少内容。
- 成功结果仍使用“点击生成时使用当前书笔记”的待生成式说明，不能准确描述已经完成的这次请求。
- 截图顶部标题被截断。如果这是页面初始位置，说明滚动容器或固定标题栏存在遮挡；如果用户此前已经滚动，则不作为布局缺陷处理。

这不是数据来源或生成链路问题，而是成功态的信息优先级问题。改造目标是让用户先看到结果，再看到低频任务入口和辅助状态。

### 16.2 改造目标

1. 成功态首屏明确回答三件事：生成了哪一种复盘、使用了多少笔记、用户下一步可以做什么。
2. 成功后只保留一个主要生成动作；复制、导出和进入完整复盘降为明确的次级动作。
3. 将来源、覆盖范围和抽样说明合并为一条可扫描信息，避免同义文案连续出现。
4. 在 1280×720 桌面视口和 390×844 窄屏视口中尽早露出结果概览，不改变完整结果的覆盖校验。
5. 保持快速/完整模式隔离、`reviewKind + inputHash` 绑定、旧快照提示和手动整理语义不变。

### 16.3 非目标

- 不改变快速复盘的抽样算法、80 条划线 + 20 条想法预算或 Provider 请求格式。
- 不改变完整复盘的快照、分批、授权、恢复、取消和失败批次重试流程。
- 不自动把快速复盘升级为完整复盘，不自动创建完整快照任务。
- 不因减少首屏卡片而删除来源统计、模型信息、整理状态或完整复盘入口。

### 16.4 成功态操作矩阵

| 当前状态 | 状态标签 | 主操作 | 次级操作 | 不应出现 |
| --- | --- | --- | --- | --- |
| 快速结果已生成 | `快速复盘已生成` | `重新生成快速复盘` | `复制快速复盘`、`导出快速复盘`、`进入完整复盘` | 禁用的 `生成快速复盘` |
| 快速生成中 | `快速复盘生成中` | `取消`（仅当请求契约支持）或等待 | 无 | 复制、导出、完整任务授权控件 |
| 快速生成失败且已有旧结果 | `快速复盘生成失败` | `重新生成快速复盘` | 复制/导出旧结果，并标记“生成时笔记” | 覆盖旧结果来源或静默重试 |
| 完整任务完成 | `完整复盘已完成` | `查看完整复盘` | `复制完整复盘`、`导出完整复盘`、`创建新快照` | 快速复盘按钮和快速正文 |
| 当前模式无结果 | `待生成` | `生成快速复盘` 或 `创建本地快照` | 切换另一模式 | 复制、导出和整理操作 |

按钮是否显示必须由当前模式和当前结果引用派生，不能因为另一个模式已有结果就显示错误的复制或导出按钮。

### 16.5 目标布局

成功态建议收敛为以下顺序：

```text
返回
书籍标题                         快速复盘已生成
本次使用 94 / 422 条笔记 · 按章节抽样，不代表全量覆盖
[重新生成快速复盘] [复制快速复盘] [导出快速复盘]

[快速复盘（抽样）] [完整复盘（快照）]
进入完整复盘：创建快照后再决定是否发送原始笔记正文

概览
关键观点
行动项
代表性摘录
复盘问题
```

具体规则：

- Hero 副标题在成功后改为“本次复盘使用有限样本生成”，不再使用“点击生成时……”的待生成文案。
- 覆盖信息使用“本次使用 x / y 条笔记”，预览或未生成状态才使用“最多使用”或“预计”。
- 快速成功态只保留一个“重新生成快速复盘”主按钮；复制和导出使用次级样式，必要时在窄屏收进更多操作菜单。
- `快速复盘 · 本次手动生成` 与有限样本解释合并成一个来源条，不再分别使用多个大卡片重复说明。
- “进入完整复盘”保留在模式切换附近，但改为紧凑 CTA；已有完整任务时显示任务状态，不能重复创建任务。
- `待整理` 保留人工确认语义，但压缩为结果标题附近的紧凑状态条，不占用与概览相同的视觉权重。
- 结果区必须设置稳定的 `id`，切换到完整结果或点击“查看完整复盘”后可滚动到对应结果标题，而不是滚动到页面中部的辅助卡片。

### 16.6 文案与来源边界

| 场景 | 推荐文案 |
| --- | --- |
| 快速生成成功 | `快速复盘已生成` |
| 快速来源 | `本次使用 94 / 422 条笔记，按章节抽样，不代表全量覆盖。` |
| 快速结果变化 | `快速复盘 · 生成时笔记；当前笔记已有变化，重新生成可纳入最新内容。` |

| 完整任务处理中 | `完整复盘进行中 · 已处理 x / y 条 · 可切换查看任务。` |
| 完整结果完成 | `完整快照复盘 · 已覆盖 x / y 条笔记。` |

来源标签、按钮无障碍名称、Toast、导出文件名和 Markdown 元数据必须使用同一模式名称。不能出现页面显示“快速复盘”而导出仍写“书籍复盘”或“本地缓存”的不一致。

### 16.8 验收标准

实施状态：已完成（2026-08-18）。

- 快速复盘成功后，首屏显示“快速复盘已生成”，不再显示禁用的“生成快速复盘”。
- 首屏在结果标题前只出现一次覆盖边界说明，且使用“本次使用”而不是“最多使用”。
- 快速成功态的复制、导出按钮只能操作快速结果；切到完整模式后不能沿用快速按钮状态。
- 完整任务完成后，首屏显示完整覆盖量、任务模型和查看完整结果入口，不显示快速结果正文。
- 桌面 1280×720 下概览标题和至少一段概览正文可见；窄屏 390×844 下按钮不重叠、不横向溢出，结果顺序不被辅助卡片推到不可见区域。
- 键盘可以聚焦模式切换、主操作和复制/导出；按钮无障碍名称包含“快速”或“完整”。
- 页面初始滚动位置不被固定标题栏遮挡；若用户已滚动，返回顶部或切书后能恢复正确标题位置。
- 生成失败时保留旧结果和来源元数据，不把错误态伪装成成功态，也不自动切换到另一模式。

### 16.9 风险与防过度设计

- 不为了减少按钮而把复制、导出隐藏到用户难以发现的纯图标菜单；窄屏才允许使用带 Tooltip 的图标入口，桌面仍保留清晰文本。
- 不删除完整复盘入口。快速结果成功后仍需要让用户能发现完整快照能力，但入口应是一个紧凑 CTA，而不是重复的大块说明卡。
- 不把“标记已整理”改成自动动作。生成成功不等于用户已经阅读、确认或执行了复盘内容。
- 不用“已生成”这种无模式状态覆盖来源边界；任何成功徽章都必须能直接区分快速和完整。

### 16.10 完整复盘专属布局

完整复盘不能直接套用快速复盘成功态的“结果优先”布局。完整模式的首要任务会随任务状态变化：未创建时是确认输入，运行中是观察和控制任务，完成后才是查看正式结果。

| 完整模式状态 | 首屏第一优先级 | 应显示 | 不应显示 |
| --- | --- | --- | --- |
| 尚未创建任务 | 确认快照范围和授权边界 | 当前笔记预览数量、预计批次、Provider/模型、授权复选框、`创建本地快照` | 快速复盘正文、完整复制/导出 |
| 已创建、等待发送 | 确认最终快照并开始发送 | 任务快照数量、实际批次、任务 Provider/模型、快照已固定说明、`开始发送并归纳` | 再次创建快照、快速生成按钮 |
| 快照/分批/归纳/合并中 | 观察进度和取消 | 已处理/总数、批次进度、任务模型、完成时间（如有）、`取消任务` | 复制、导出、授权复选框、继续创建任务 |
| 部分失败 | 只处理失败批次 | 失败批次编号、错误摘要、已处理数量、`重试失败批次` | 持续轮询、完整成功标签、把部分结果当正式完整结果 |
| 失败且无可重试批次 | 解释终态并重新开始 | 错误原因、`创建新的快照` | `继续归纳`、完整复制/导出 |
| 已取消 | 保留结果和重新开始入口 | 已取消状态、已处理进度、`创建新的快照` | `继续归纳`、完整成功标签 |
| 完成且通过覆盖校验 | 查看正式成果 | `完整复盘已完成`、快照覆盖量、任务模型、结果正文、复制/导出 | 快速复盘正文、快速结果来源标签 |
| 完成但快照过期 | 区分历史成果和当前来源 | `完整快照复盘 · 旧快照`、旧快照说明、复制/导出（带旧快照标识）、`创建新快照` | 宣称覆盖当前笔记、静默替换为快速结果 |
| 有结果但引用未验证 | 保守展示历史资产 | `历史结果 · 来源未验证`、创建新快照提示 | 完整覆盖文案、完整复制/导出或反馈操作 |

完整模式已显示正式结果时，任务卡应收敛为覆盖摘要和任务元数据；“查看完整复盘”只在快速模式的轻量任务入口或其他页面跳转入口中出现，不能在完整结果正文上方重复占据主操作位。

### 16.11 快照统计一致性

完整复盘必须区分“预览统计”和“任务快照统计”：

- 没有任务时，使用 `preview` 展示当前笔记数量、类型计数、预计批次和字符估算，并标注“预览”。
- 已创建任务后，任务卡标题、进度、批次和来源边界统一使用 `activeJob` 的 `totalCount`、`processedCount`、`batchCount` 和 `coverage`；不能继续把当前笔记预览数量当成任务输入。
- 当前笔记在任务创建后发生变化时，单独显示“当前笔记已有变化；任务仍基于创建时快照”，不能用当前数量覆盖任务数量，也不能把差异误报为任务失败。
- `estimatedBatchCount` 只用于创建前预估；任务创建后必须显示实际 `batchCount` 和已完成批次。
- 完整结果来源文案中的 `x / y` 必须来自经过覆盖校验的任务快照，不能来自搜索命中数、向量索引数量或当前页面笔记数组。

验收至少覆盖：预览后新增笔记、预览后删除笔记、预览后正文修改，以及创建任务后继续新增笔记。所有场景都必须满足“任务输入统计不变，当前来源变化单独提示”。

### 16.12 完整预览失败与恢复

完整模式读取 `previewNoteSynthesis` 或最近任务摘要失败时，不能静默显示“待生成”或空白任务区：

- 显示独立错误卡，说明“完整复盘预览读取失败”，并提供 `重新读取完整复盘状态`；
- 预览失败期间禁用 `创建本地快照` 和授权复选框，避免用户在未确认输入范围时创建任务；
- 不回退展示快速复盘正文，也不把快速结果数量当作完整预览数量；
- 重试成功后用服务端返回的最新预览和任务摘要重建页面；
- 重试期间保留当前模式，不自动跳回快速模式，不重复弹出 Provider 授权确认。

如果已有可验证的活动任务而预览接口暂时失败，应优先显示任务摘要和“重新读取状态”，不能创建新任务；如果既没有预览也没有活动任务，才显示无法创建完整快照的错误空态。

### 16.13 按状态区分首屏验收

“首屏露出概览”只适用于已经成功生成结果的状态，不能压过完整任务的授权和进度信息：

| 视口 | 快速成功 | 完整未创建/等待发送 | 完整运行中/部分失败 | 完整成功/旧快照 |
| --- | --- | --- | --- | --- |
| 1280×720 | 概览标题和至少一段正文可见 | 快照数量、授权或开始发送按钮可见 | 进度、失败批次或取消/重试按钮可见 | 完整覆盖量、模型和结果标题可见 |
| 390×844 | 标题、来源边界和主操作不重叠 | 授权说明和创建/开始按钮可滚动触达 | 进度和重试/取消按钮保持可操作 | 完整结果标题和复制/导出入口可触达 |

完整任务状态下，任务卡可以占据首屏主要空间；不能为了让概览提前出现而隐藏授权、快照范围、失败批次或取消操作。

### 16.14 完整模式操作去重

- 完整任务完成且当前已经处于完整模式时，任务卡只保留覆盖摘要、旧快照提示（如有）和必要的 `创建新快照`；结果区承担复制、导出和反馈。
- 快速模式看到完整任务轻量入口时，入口按钮可以叫 `查看完整复盘`，点击后切换到完整模式并滚动到结果或任务卡。
- 完整模式的 `开始发送并归纳` 只能在快照已经创建、任务状态为 `queued` 且授权已确认时出现；不能用一个“生成完整复盘”按钮合并创建快照和发送正文两个动作。
- `复制完整复盘` 和 `导出完整复盘` 只有在完整结果通过任务、覆盖和结果引用三重校验后出现；部分失败、失败、取消和未验证结果不提供正式完整导出。

### 16.15 完整复盘测试补充

P1.8 实施时需要新增或补齐以下测试：

- 完整模式尚未创建任务时只显示授权和创建快照，不显示快速正文；
- `queued` 状态只显示开始发送，不显示重复创建快照；
- `snapshotting/batching/summarizing/merging` 显示任务进度和取消入口，且不显示复制/导出；
- `partial` 只允许重试失败批次，不持续轮询，不标记为完整成功；
- `failed/cancelled` 提供创建新快照，不提供继续归纳；
- 完整成功显示任务快照覆盖量、模型和正式结果；
- 完整旧快照允许带标记复制/导出，并提供创建新快照；
- 完整预览读取失败显示错误和重试，不回退到快速结果；
- 任务创建前后笔记数量变化时，任务统计仍绑定不可变快照；
- 1280×720 和 390×844 下完整授权、进度、失败批次、结果和操作区均可触达且无溢出。
